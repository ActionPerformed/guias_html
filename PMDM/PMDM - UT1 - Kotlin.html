Introducción y configuración

Por qué Kotlin ha ganado terreno en Android y qué necesitas instalado antes de escribir la primera línea.

¿Por qué Kotlin?

  • Lenguaje preferido para Android desde 2019; su soporte oficial por parte de Google se anunció en 2017.
  • Interoperable con Java de forma práctica: puedes llamar a clases Java desde Kotlin y al revés, aunque hay diferencias que conviene conocer (los platform types, el null de Java y las excepciones checked).
  • Null Safety: el compilador traslada el error de nulos al momento de compilar y te obliga a decidir qué hacer. No desaparece: si más tarde usas !! o llamas a una API de Java, la NullPointerException sigue siendo posible.
  • Conciso: elimina la mayor parte del boilerplate de getters/setters, constructores y campos finales. Cuánto código te ahorra depende de cómo escribías el Java de partida.
  • Moderno: combina programación orientada a objetos y funcional.

Variables, tipos, seguridad ante nulos, cadenas, rangos y estructuras de control: la caja de herramientas que usarás en cada línea de código.

Concepto clave: por defecto, las variables NO pueden ser null.

var ciudad: String? = null   // ✅ Válido (nullable)
var pais: String = null      // ❌ ERROR de compilación

El mensaje real del compilador es el que te dice qué ha pasado. Para la segunda línea, Kotlin muestra:

// Type mismatch: inferred type is Nothing? but String was expected

Qué significa: a pais le has asignado null, y el compilador deduce que su tipo sería Nothing? (el tipo de null). Pero la variable está declarada como String, que no admite nulos: por eso no encajan. Fíjate en que el error te dice el tipo que ha deducido y el que esperabas; es la misma idea que el mensaje de Java, solo que más explícito.

Cuidado con !!: reintroduce el mismo riesgo de NullPointerException que Kotlin intenta evitar. Úsalo solo cuando estés absolutamente seguro de que el valor no será nulo. Antes de recurrir a él, elige la alternativa que corresponda:
Situación Alternativa a !!
El nulo es posible y hay una acción alternativa ciudad?.length (operador safe call)
El nulo es posible y hay un valor por defecto ciudad ?: "Desconocida" (operador Elvis)
Solo quieres trabajar si no es nulo ciudad?.let { … } o ciudad?.run { … }
El nulo es un bug de lógica, no un caso previsto requireNotNull(ciudad) { "La ciudad no puede ser nula" }

La última es la clave: requireNotNull no lanza una NPE genérica, sino un IllegalArgumentException con el mensaje que tú escribas. Si el nulo es un error de programación, esto documenta la intención y falla en el sitio correcto.

Exhaustividad: cuándo es obligatorio el else.
  • Con Int, String o cualquier tipo abierto: el else es obligatorio, porque puede haber valores que no has cubierto.
  • Con un sealed class o un enum class: el else es opcional, porque el conjunto de casos posibles está cerrado. Si añades un caso nuevo a la jerarquía y no lo cubres, el compilador deja de compilar: eso es exactamente lo que se busca, para que nadie se olvide de un estado.

El for de Kotlin no usa índices… y no hay que implementar ningún Iterator. En Java, el for-each funciona porque Iterable declara un método iterator() que devuelve un Iterator con hasNext() y next(), y tú implementas esa interfaz cuando creas tu propia colección. En Kotlin el for recorre cualquier iterable y el compilador genera el iterador por ti: tú no implementas nada. Cuando lo que necesitas es el índice, usa withIndex() (como en el ejemplo de arriba), que te da ambos valores a la vez.
Del bucle clásico a la cadena de operadores. Los operadores filter, map y compañía no son «magia»: son el resultado de encadenar transformaciones, y su equivalente en Java es el bucle con for (o, si ya usabas Java 8, una cadena de Stream). Las tres formulaciones hacen lo mismo:
val alumnos = listOf("Ana", "Bea", "Carlos", "Ana", "David")

// 1) Kotlin clásico: bucle con índice
val conA = mutableListOf<String>()
for (i in alumnos.indices) {
    if (alumnos[i].startsWith("A")) conA.add(alumnos[i])
}
println(conA)   // [Ana, Ana]

// 2) Kotlin funcional: la misma operación, encadenada
val conA2 = alumnos.filter { it.startsWith("A") }
println(conA2)  // [Ana, Ana]

// 3) Java 8+: el equivalente con Streams
// List<String> conA3 = alumnos.stream()
//     .filter(a -> a.startsWith("A"))
//     .collect(Collectors.toList());
¿Cuándo usar cada uno? El bucle for cuando necesitas modificar algo durante el recorrido, romper (break) o continuar (continue), porque las cadenas de operadores se leen bien pero no admiten esas dos cosas. La cadena de operadores cuando solo quieres transformar una colección: se lee de izquierda a derecha y cada paso es un valor intermedio.

En Java, para comprobar el tipo de un objeto hay que escribir instanceof y, después, hacer una conversión explícita ((Exito) estado) para poder acceder a los miembros propios de ese tipo. Kotlin tiene herramientas para las dos cosas, y además el compilador se charge de la conversión cuando puede.

Operador Qué hace Equivalente en Java
is Devuelve true si el objeto es de ese tipo (o de un subtipo) instanceof
as Convierte el objeto. Si no es del tipo, lanza ClassCastException (Exito) estado
as? Convierte con seguridad: si no es del tipo, devuelve null en lugar de fallar No hay equivalente directo
smart cast Tras comprobar con is, el compilador ya sabe el tipo y te deja acceder a sus miembros sin escribir nada No hay equivalente: en Java hay que castear a mano 
sealed class EstadoUI<out T> {
    data object Cargando : EstadoUI<Nothing>()
    data class Exito<T>(val datos: T) : EstadoUI<T>()
    data class Error(val mensaje: String) : EstadoUI<Nothing>()
}

val estado: EstadoUI<List<String>> = EstadoUI.Exito(listOf("Ana"))

// 'is' comprueba el tipo y devuelve un Boolean
if (estado is EstadoUI.Exito) {
    // SMART CAST: aquí el compilador ya sabe que 'estado' es Exito,
    // así que deja acceder a .datos sin escribir ningún cast.
    println(estado.datos)   // [Ana]
}

// 'as' convierte; si el tipo no encaja, lanza ClassCastException
val exito = estado as EstadoUI.Exito<List<String>>
println(exito.datos)       // [Ana]

// 'as?' convierte con seguridad: devuelve null si no encaja
val error = estado as? EstadoUI.Error
println(error?.mensaje)    // null (no es un Error)

// En Java habría que escribir:
// if (estado instanceof Exito) { ((Exito) estado).getDatos(); }
Cuándo funciona el smart cast (y cuándo no). El compilador solo lo aplica si puede garantizar que el tipo no va a cambiar entre la comprobación y el uso. Funciona con: variables val locales, propiedades val de la misma clase, y objetos que no se puedan mutar. No funciona con una var local (porque podría cambiar), ni con una propiedad var de otra clase, ni con un var abierto que otro código pueda modificar. En esos casos Kotlin te pide un cast explícito, y por eso no debes fiarte de un smart cast que no compile: es que la garantía no se cumple.
// Con 'val' el smart cast funciona
val texto: Any = "Hola"
if (texto is String) {
    println(texto.length)   // 4  -> el compilador ya sabe que es String
}

// Con 'var' NO se puede hacer smart cast: el tipo puede cambiar
var cualquiera: Any = "Hola"
if (cualquiera is String) {
    // println(cualquiera.length)  -> error de compilación
    // hay que castear a mano:
    println((cualquiera as String).length)   // 4
}
Equivalencias con Java, de un vistazo:
  • Unit ≈ void (y Void): el valor de «nada». Kotlin, además, permite Any como tipo de retorno real.
  • Nothing ≈ no existe equivalente en Java: es el tipo de una función que nunca termina de forma normal (porque lanza). Como es el tipo inferior, el compilador acepta una función Nothing allí donde se espera cualquier otro tipo.
  • Any ≈ Object, pero solo para tipos no anulables; el equivalente real de Object es Any?.

Este es el cambio de semántica más silencioso que vas a notar, porque los símbolos son los mismos pero significan lo contrario. En Java, para objetos, == compara referencias y el contenido se compara con equals(). En Kotlin está al revés: == compara valor (invoca equals() por debajo) y la identidad de referencia se pide con ===.

Expresión Qué compara Equivalente en Java
a == b Valor: llama a equals(). Dos objetos con los mismos campos son iguales a.equals(b)
a === b Identidad: ¿son el mismo objeto en memoria? a == b
a != b Negación de == !a.equals(b)
a !== b Negación de === a != b

    override fun equals(otro: Any?): Boolean =
        otro is Articulo && id == otro.id

    override fun hashCode(): Int = id
}

Por qué equals() y hashCode() van siempre juntos. Son dos preguntas distintas: equals() dice «¿son el mismo valor?» y hashCode() dice «¿en qué cubo los meto?». Las colecciones hash (HashMap, HashSet) usan el hashCode() para encontrar el cubo y el equals() para confirmar la coincidencia. Si dos objetos son iguales pero tienen distinto hashCode(), buscarán en cubos distintos y nunca se encontrarán. Por eso, si escribes equals(), escribe también hashCode(). Una data class te da los dos ya hechos.
La trampa del data class con ByteArray. El equals() generado compara sus propiedades con ==, pero ByteArray se compara por referencia, no por contenido. Dos Completada con los mismos bytes no son iguales. Para comparar el contenido, usa contentEquals():
// contentEquals() compara el CONTENIDO del array
val a = byteArrayOf(1, 2, 3)
val b = byteArrayOf(1, 2, 3)
println(a == b)                      // false -> compara referencias
println(a.contentEquals(b))          // true  -> compara el contenido

Bloque init (inicialización):

class Persona(val nombre: String, val anioNacimiento: Int) {
    val edad: Int

    init {
        edad = 2026 - anioNacimiento
        println("Persona creada: $nombre ($edad años)")

init no es un constructor, y Kotlin sí tiene constructores secundarios. En Java, el cuerpo del constructor va dentro del new Persona(...). En Kotlin el constructor primario es solo la lista de parámetros (no tiene cuerpo), y el bloque init { } es un bloque de inicialización que se ejecuta al crear el objeto: es el equivalente al cuerpo del constructor de Java. Si necesitas constructores adicionales, existen los secundarios, y se escriben con la palabra constructor:
class Persona(val nombre: String, val anioNacimiento: Int) {
    val edad: Int
    var email: String? = "sin email"
        private set

    init {
        edad = 2026 - anioNacimiento
        println("Persona creada: $nombre ($edad años)")
    }

    // Constructor secundario: además del nombre y el año, se pasa el email.
    // Al tener OTRA firma, no choca con el constructor primario.
    constructor(nombre: String, anioNacimiento: Int, email: String) : this(nombre, anioNacimiento) {
        this.email = email
    }
}

val anonima = Persona("Ana", 1995)
val conEmail = Persona("Bea", 1998, "bea@email.com")
println(conEmail.email)   // bea@email.com
El orden de inicialización importa. Las propiedades se inicializan en el orden en que están declaradas, y los bloques init se ejecutan en su sitio, intercalados. Por eso una propiedad declarada después no puede usarse desde un init anterior: el compilador no la conoce todavía. Y el this en un constructor secundario delega en el primario (debe ser la primera instrucción), de modo que la inicialización no se duplica.
  • Las clases son final por defecto: no se pueden heredar. Hay que marcarlas open.
  • Los miembros también son final por defecto: un método no se puede sobrescribir salvo que esté marcado open. El modificador override no sustituye al open: se necesitan los dos.
  • El override es obligatorio (en Java es opcional): si sobrescribes un método sin escribirlo, el compilador da un error. Kotlin te obliga a declarar la sobrescritura, para que quien lea el código la vea sin tener que subir a la clase padre.
  • Las propiedades val no se pueden sobrescribir nunca (no tienen setter).
open class Animal(val nombre: String) {
    open fun sonido() = "Sonido genérico"  // open: se puede sobrescribir
    fun respirar() = println("Respirando")     // final: nadie lo puede cambiar
}

class Perro(nombre: String, val raza: String) : Animal(nombre) {
    override fun sonido() = "Guau!"
}

// Uso
val perro = Perro("Max", "Labrador")
println(perro.sonido())  // Guau!
Ojo con los parámetros del constructor que no llevan val ni var: en Perro(nombre: String, ...), nombre es solo un parámetro: se usa para pasárselo al constructor del padre (Animal(nombre)) y luego desaparece; no existe como propiedad de Perro. La propiedad nombre vive en Animal. Si quisieras redeclararla en Perro, tendrías que escribir override val nombre: String en el constructor primario y pasarle el valor al padre.

Ventajas: genera automáticamente toString(), equals(), hashCode(), copy().

data class Usuario(val id: Int, val nombre: String, val email: String)

val usuario1 = Usuario(1, "Ana", "ana@email.com")

Dos detalles que conviene saber:
  • data class solo mira las propiedades declaradas en el constructor primario. Las propiedades del cuerpo de la clase (val activo = true) o de un constructor secundario no entran en el equals() ni en el toString() generados.
  • Además genera component1(), component2(), … por cada propiedad del constructor primario, lo que permite destructurar una instancia con el val (a, b) = punto.
data class Punto(val x: Int, val y: Int) {
    val etiqueta: String = "sin etiqueta"  // NO entra en equals() ni en toString()
}

val (px, py) = Punto(3, 4)          // Desestructuración: px=3, py=4
println(px + py)                      // 7
println(Punto(3, 4))                   // Punto(x=3, y=4)  -> la etiqueta no aparece
El equals() de una data class es igualdad estructural, no referencial. Dos Usuario con los mismos datos son == aunque sean objetos distintos en memoria. En Java, dos objetos con los mismos campos NO eran iguales salvo que hablaras de un record o escribieras el equals() a mano: es el mismo salto conceptual que el de los data class en sí. El detalle está en el apartado 2.8 «Igualdad e identidad».
Importante para Android: modelar estados de UI.

Con un tipo genérico, el mismo sealed class sirve para estados con contenidos distintos: EstadoUI<List<String>> en un caso y EstadoUI<List<Producto>> en otro. El out indica que ese tipo solo se entrega, nunca se recibe: por eso EstadoUI<Nothing> —el estado «sin datos»— sirve como valor inicial de cualquiera.

Varianza: qué significa el out (y el in). En Java, los genéricos son invariantes: List<String> no es un List<Any>, aunque String sea un Any. Kotlin añade varianza declarativa: se declara en la definición del tipo, con dos palabras reservadas.
  • out T («productor»): el tipo solo se entrega. Kotlin te deja usar EstadoUI<List<String>> donde se espera EstadoUI<List<Any>>, porque solo vas a leer. Equivale a ? extends T en Java.
  • in T («consumidor»): el tipo solo se recibe. Equivale a ? super T en Java.
  • Sin declaración, el tipo es invariante, igual que en Java.

Por eso EstadoUI<Nothing> funciona como estado «sin datos» de cualquier variante: Nothing es el tipo inferior (el único tipo que es subclase de todos), así que es asignable a cualquier T. Es el mismo truco que List<Nothing> como lista vacía.

sealed class EstadoUI<out T> {
    data object Cargando : EstadoUI<Nothing>()
    data class Exito<T>(val datos: T) : EstadoUI<T>()
    data class Error(val mensaje: String) : EstadoUI<Nothing>()
}

// Uso con when (cubre todos los casos)
fun manejarEstado(estado: EstadoUI<List<String>>) {
    when (estado) {
        is EstadoUI.Cargando -> println("Mostrar loading...")
        is EstadoUI.Exito -> println("Datos: ${estado.datos}")
        is EstadoUI.Error -> println("Error: ${estado.mensaje}")
    }
}
Qué significa sealed (sellada):
  • Jerarquía cerrada: las subclases se declaran dentro de la clase sellada (en el mismo archivo, en Kotlin 1.5+). Nadie puede añadir un caso nuevo desde fuera, así que el conjunto de estados posibles es conocido y finito.
  • Sigue siendo final: una sealed class no se puede heredar de ella; solo se ramifica por sus subclases.
  • El when es exhaustivo: no hace falta else, y el compilador obliga a cubrir todos los casos. Si añades data object Vacio a la jerarquía y no lo tratas, el código deja de compilar. Eso es justo lo que se busca: ningún estado se queda sin atender.
  • También existe sealed interface (Kotlin 1.5+), que hace lo mismo pero con una interfaz: útil cuando los casos no comparten implementación. Y data object (Kotlin 1.9+) es la forma moderna de escribir object Cargando: le da toString() y equals() propios, como cualquier data class.

Cuando llegues a las actividades del módulo verás las dos formas; no son dos conceptos distintos, es la misma idea con dos sintaxis.

Qué es field (la «propiedad de respaldo»): es el campo privado que el compilador genera por ti detrás de la propiedad, donde se guarda de verdad el valor. Sintaxis de lambda:

val suma: (Int, Int) -> Int = { a, b -> a + b }

El it implícito solo existe con un parámetro. En cuanto la lambda tiene dos o más, Kotlin exige que los nombres: { x, y -> x + y }. Si uno de ellos no lo vas a usar, puedes ponerlo como _ (guion bajo) desde Kotlin 1.9: { x, _ -> x }. // fun toInitials(this: String): String
// El receptor (this) es el primer parámetro.
fun String.toInitials(): String =
    this.split(" ")
        .filter { it.isNotBlank() }
        .map { it.first().uppercase() }
        .joinToString(".") + "."

Cinco funciones que permiten trabajar «dentro» de un objeto: let, run, apply, also y with. Se diferencian en cómo se referencia al objeto y en qué devuelven.

Regla de elección: ¿cuál uso? No hace falta memorizar las cinco: decide primero qué quieres que devuelva la expresión y qué necesitas del objeto.
  • let: quieres transformar el objeto y devolver otro valor distinto (o una cadena). Es la que usas con los nullable, porque solo se ejecuta si no es null.
  • apply: quieres configurar el objeto y devolver el mismo objeto, para encadenar. Es el patrón «builder».
  • also: quieres un efecto secundario (log, validación, métricas) y devolver el objeto sin tocarlo.
  • with: quieres agrupar varias llamadas sobre un objeto que ya sabes que no es nulo. No es una función de extensión: se escribe with(objeto) { ... } con el objeto dentro de los paréntesis, y no admite ?. ni ?: porque el objeto se evalúa antes de entrar.
  • run: como let pero con this en lugar de it. Útil cuando dentro de la lambda necesitas llamar a varios métodos del propio objeto.

Manejo de excepciones

En Kotlin, try también puede ser una expresión, y runCatching lleva ese estilo funcional hasta el manejo de errores.

try-catch como expresión

val resultado = try {
    val numero = "123".toInt()
    numero * 2
} catch (e: NumberFormatException) {
    -1  // Valor por defecto si falla
}
El catch debe devolver el mismo tipo que el try: el try devuelve un Int (numero * 2), así que el catch está obligado a devolver también un Int: por eso el -1. Si el catch devolviera un String, el compilador se quejaría de que los dos caminos no tienen el mismo tipo. Y si te da igual el valor, la forma idiomática es catch (e: Exception) { null } con un tipo Int?.

runCatching (funcional)

val resultado = runCatching {
    "abc".toInt()  // Lanza excepción
}.getOrElse {
    -1  // Valor por defecto
}

// Otros métodos útiles
val exito = runCatching { 42 }
    .getOrNull()  // null si falla

val mensaje = runCatching { "123".toInt() }
    .fold(
        onSuccess = { "Éxito: $it" },
        onFailure = { "Error: ${it.message}" }
    )
Tip: runCatching devuelve un Result<T>, así que encaja bien en cadenas funcionales donde no quieres romper el flujo con un try/catch tradicional.
La API de Result<T> que vas a necesitar:
  • isSuccess / isFailure: si funcionó o no.
  • getOrThrow(): devuelve el valor o relanza la excepción (útil en un try/catch normal).
  • onSuccess { } / onFailure { }: ejecuta una acción según el caso y devuelve el mismo Result, así que se pueden encadenar.
  • mapCatching { }: transforma el valor si funcionó; si falla, propaga el fallo.
  • recoverCatching { }: si falló, ejecuta otro bloque para recuperar un valor válido (por ejemplo, devolver una lista vacía).
  • fold(onSuccess, onFailure): como un if/else sobre el resultado.
getOrElse { -1 } confunde dos cosas: si el valor real fuera -1, no sabrías si la operación funcionó o no. La lambda de getOrElse recibe la excepción como parámetro ({ e -> ... }), así que puedes usarla: getOrElse { e -> -1 }. Si necesitas distinguir los casos, usa getOrNull() junto con isFailure, o fold, que te da las dos ramas por separado.
runCatching se traga la cancelación de las corrutinas. Captura cualquier Throwable, y eso incluye la CancellationException que Kotlin usa para cancelar una corrutina: si la tragas, la corrutina «sigue viva» cuando debería detenerse, y la cancelación se pierde. Dentro de una corrutina, usa try/catch normal y captura solo las excepciones que te interesen.
Kotlin no tiene excepciones «checked» (comprobadas). En Java, el compilador te obligaba a declarar o capturar las excepciones checked que declara un método. En Kotlin no existen: ninguna función necesita throws y el compilador no te fuerza a capturarlas. Solo se capturan las que tú decidas. Esto cambia la interoperabilidad: cuando llames a una API de Java que declare throws IOException, Kotlin te deja llamarla sin nada; el compilador no te avisa, así que la responsabilidad de comprobarla es tuya.
Si Java necesita saberlo, se lo dices con @Throws. Kotlin puede anotar una función para que, en el bytecode generado, declare la excepción que Java espera. Es el puente para escribir una función en Kotlin que llamen código Java:
import java.io.IOException

// En Kotlin NO se escribe 'throws'. Si quien llama es Java y
// espera una IOException, se declara con la anotación @Throws:
@Throws(IOException::class)
fun leerDeFichero(ruta: String): String {
    // Aquí dentro tú decides si capturarla o no
    return java.io.File(ruta).readText()
}

Corrutinas — asincronía moderna

La forma en la que Kotlin resuelve las operaciones que tardan (red, disco, temporizadores) sin bloquear el hilo principal ni encadenar callbacks.

// build.gradle.kts
dependencies {
    implementation("org.jetbrains.kotlinx:kotlinx-coroutines-core:1.7.3")
    implementation("org.jetbrains.kotlinx:kotlinx-coroutines-android:1.7.3")
}

Conceptos básicos

Concepto Descripción
suspend Función que puede pausarse y reanudarse
CoroutineScope Ámbito de vida de las corrutinas
Dispatchers Contexto que decide en qué hilo se ejecuta el código (Main, IO, Default)
Job Representa una tarea cancelable
launch Lanza corrutina y devuelve un Job
async Lanza corrutina y devuelve un Deferred<T> (un Job que además lleva el resultado)
Un Dispatcher no es un hilo: es un contexto. Un hilo es un recurso del sistema; un contexto es «en qué tipo de hilo y con qué prioridad se ejecuta esto». El criterio para elegir:
  • Dispatchers.IO → trabajo bloqueante: red, disco, base de datos, leer un fichero. Es un pool de hilos pensado para esperar.
  • Dispatchers.Default → trabajo de CPU: cálculos, compresión, análisis de ficheros en memoria. Si el trabajo no espera nada y solo calcula, es este.
  • Dispatchers.Main → el hilo principal de Android, el único que puede tocar la interfaz. En Android Studio con Compose o con Views, la UI se actualiza desde aquí.

Una corrutina puede cambiar de dispatcher en mitad de su ejecución con withContext(Dispatchers.IO) { ... }: dentro del bloque se ejecuta en IO y al salir vuelve al dispatcher anterior.

launch frente a async: los dos devuelven algo. launch devuelve un Job, que sirve para esperar (join()) o cancelar (cancel()), pero no lleva resultado. async devuelve un Deferred<T>, que es un Job que además transporta el valor, y se lee con await(). Regla práctica: si no vas a usar el valor, usa launch; un async al que nunca llamas await() es un error de estilo (además, su excepción se queda guardada y no se propaga).
join() frente a await(): join() espera a que la corrutina termine, pero no te da nada y no relanza la excepción si la hubo. await() espera y además devuelve el resultado; si la corrutina falló, relanza la excepción en el punto de la llamada, como si el try/catch lo rodease. Y runBlocking bloquea el hilo en el que se ejecuta: solo tiene sentido en el main de una aplicación de consola o en una prueba unitaria. En Android nunca debes usarlo, porque bloquearías el hilo principal y la interfaz se congelaría.
awaitAll(): cuando hay varias corrutinas en paralelo. Si lanzas varias corrutinas con async y quieres todas sus resultados, no esperas una a una: awaitAll() espera a todas y devuelve la lista de resultados en el mismo orden en que las creaste. Si alguna falla, awaitAll() relanza su excepción, igual que await(). Es el equivalente a CompletableFuture.allOf(...).join() en Java.
Concurrencia estructurada: toda corrutina pertenece a un CoroutineScope, y cuando ese ámbito se cancela o termina, todas sus corrutinas hijas se cancelan también. No hay corrutinas «sueltas»: por eso Android ofrece viewModelScope (se cancela solo cuando el ViewModel se destruye) y lifecycleScope (idem al destruirse la pantalla). Para crear un ámbito anidado dentro de una función suspend, usa coroutineScope { }: es el equivalente idiomático a runBlocking, pero no bloquea el hilo y propaga los errores al ámbito padre.
import kotlinx.coroutines.*

suspend fun obtenerUsuarios(): List<String> {
    delay(100)
    return listOf("Ana", "Bea")
}

suspend fun obtenerPedidos(): List<String> {
    delay(200)
    return listOf("Pedido 1")
}

// coroutineScope: ámbito anidado, espera a que terminen y propaga los errores
suspend fun cargarTodo(): List<String> = coroutineScope {
    val usuarios = async { obtenerUsuarios() }
    val pedidos = async { obtenerPedidos() }
    usuarios.await() + pedidos.await()
}

// El ámbito espera a las dos y devuelve el resultado
fun main() = runBlocking {
    println(cargarTodo())
}

import kotlinx.coroutines.*

// Función suspendida
suspend fun obtenerDatos(): String {
    delay(1000)  // Simula operación lenta
    return "Datos cargados"

fun main() = runBlocking {
    // launch: sin retorno
    val job = launch(Dispatchers.IO) {
        val datos = obtenerDatos()
        println("Resultado: $datos")
    }
    job.join()  // Espera a que termine

    // async: con retorno
    val deferred = async(Dispatchers.IO) {
        obtenerDatos()
    }
    val resultado = deferred.await()
    println(resultado)
}

Manejo de errores

import kotlinx.coroutines.*

fun main() = runBlocking {
    val handler = CoroutineExceptionHandler { _, exception ->
        println("Error capturado: ${exception.message}")

        throw RuntimeException("Error en corrutina")
    }

CoroutineExceptionHandler tiene dos limitaciones que conviene conocer:
  • No se aplica a async. En una corrutina creada con async, la excepción no se propaga de inmediato: queda guardada en el Deferred y se relanza en el punto donde llames a await(). Por eso el try/catch alrededor del await() es lo que la captura, no el handler.
  • Una excepción no capturada en un launch cancela el ámbito padre. Es el comportamiento de la concurrencia estructurada: si una corrutina hija falla, las hermanas se cancelan y el error sube hasta el scope. Si quieres que una corrutina pueda fallar sin arrastrar a las demás, usa un SupervisorJob como padre del ámbito.
import kotlinx.coroutines.*

// Con async, la excepción se relanza en el await(): ahí se captura
fun main() = runBlocking {
    val deferred = async {
        throw RuntimeException("Error en corrutina")
    }
    try {
        deferred.await()
    } catch (e: RuntimeException) {
        println("Error capturado: ${e.message}")
    }

En Android (viewModelScope)

// apiService sería el cliente HTTP (Retrofit, Ktor...) inyectado en el ViewModel
interface ApiService {
    suspend fun obtenerDatos(): List<String>
}

class MiViewModel(private val apiService: ApiService) : ViewModel() {
    private val _estado = MutableStateFlow<EstadoUI<List<String>>>(EstadoUI.Cargando)

    fun cargarDatos() {
        // viewModelScope ya usa Dispatchers.Main.immediate: no hay que cambiarlo aquí
        viewModelScope.launch {
            _estado.value = EstadoUI.Cargando
            try {
                val datos = apiService.obtenerDatos()   // La API suspend ya devuelve en IO
                _estado.value = EstadoUI.Exito(datos)
            } catch (e: CancellationException) {
                throw e   // La cancelación se propaga: NO se captura
            } catch (e: Exception) {
                _estado.value = EstadoUI.Error(e.message ?: "Error")
            }
        }
    }
}
Dos anti-patrones que verás mucho en tutoriales y conviene no copiar:
  • viewModelScope.launch(Dispatchers.IO): viewModelScope ya viene configurado con Dispatchers.Main.immediate. Cambiarlo a IO no aporta nada y, si el ViewModel actualiza estado que la UI lee, complica la vida. El dispatcher se decide dentro del repositorio, en la capa que hace la E/S.
  • withContext(Dispatchers.Main) { _estado.value = ... }: no hace falta. StateFlow.value es thread-safe: puedes escribirlo desde cualquier hilo, y la UI recibe el cambio de forma segura. El salto a Main es ruido.
  • catch (e: Exception) sin más: CancellationException es una Exception, así que ese catch se traga la cancelación de la corrutina y la deja en un estado raro. Captúrala y vuelve a lanzarla, como en el ejemplo de arriba.
De dónde sale viewModelScope y hasta cuándo vive. Es una extensión que la librería de AndroidX (androidx.lifecycle:lifecycle-viewmodel-ktx) define sobre cualquier ViewModel. Crea un CoroutineScope ligado al ciclo de vida del ViewModel: cuando la pantalla se destruye y el ViewModel se limpia, el scope se cancela y todas las corrutinas que estaban dentro se cancelan solas. Por eso no hace falta cancel() a mano ni guardar el Job en ninguna variable: el framework se encarga.

La alternativa para el código de la Activity es lifecycleScope, que funciona igual pero ligado al ciclo de vida de la pantalla: se cancela cuando la Activity se destruye. La regla práctica: las corrutinas que piden datos van en el ViewModel (sobreviven a los cambios de configuración, como girar la pantalla) y las que pintan en pantalla van en la Activity.

Flow y StateFlow: el estado de la pantalla

Un Flow es una fuente de valores que se recolecta: algo que emite datos a lo largo del tiempo y al que te «suscribes» con collect { }. Es el sustituto de los callbacks y de los LiveData en el mundo moderno de Android.

Tipo Qué es Se puede escribir desde fuera
Flow<T> Secuencia de valores. Es «frío»: el bloque que emite no se ejecuta hasta que alguien lo recolecta, y se vuelve a ejecutar por cada recolector No (solo se emite desde dentro del flujo)
StateFlow<T> Como un Flow, pero siempre tiene un valor actual. Es «caliente»: existe aunque nadie lo esté mirando, y cuando alguien lo recolecta recibe primero el valor actual y después los nuevos No
MutableStateFlow<T> La versión escribible del anterior. Es la que vive dentro del ViewModel Sí, con .value = ... 
import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

// Un Flow 'frío': el código se ejecuta cada vez que alguien lo recolecta
fun temperaturas(): Flow<Int> = flow {
    for (t in listOf(18, 21, 25)) {
        emit(t)
    }
}

fun main() = runBlocking {
    // 'collect' recibe cada valor emitido
    temperaturas().collect { t -> println("$t grados") }
}
Por qué el StateFlow se expone como private val _uiState + val uiState = _uiState.asStateFlow(). Es una convención de Android que conviene aprender ya: la propiedad con guion bajo es privada (solo el ViewModel puede escribir en ella) y la pública es de solo lectura, porque asStateFlow() devuelve una vista de solo lectura del MutableStateFlow. Así nadie de fuera puede hacer vm.uiState.value = ... y romper el estado. La Activity solo puede escuchar.
import kotlinx.coroutines.flow.*

// El estado de la pantalla (la misma sealed class de la sección 3.5)
sealed class EstadoUI<out T> {
    data object Cargando : EstadoUI<Nothing>()
    data class Exito<T>(val datos: T) : EstadoUI<T>()
    data class Error(val mensaje: String) : EstadoUI<Nothing>()
}

// Dentro del ViewModel: se escribe en privado...
private val _uiState = MutableStateFlow<EstadoUI<List<String>>>(EstadoUI.Cargando)

// ...y se expone de solo lectura
val uiState: StateFlow<EstadoUI<List<String>>> = _uiState.asStateFlow()

// 'asStateFlow' NO copia el valor: es una vista del mismo flujo.
// Por eso el valor inicial (Cargando) se ve al instante al recolectarlo.
collect nunca termina (es un bucle infinito esperando valores), así que no puedes llamar a collect directamente en el main de una app de consola: el programa se quedaría colgado. Para probarlo en el Playground, o para leer un solo valor y seguir, usa first() (devuelve el valor actual y termina) o first { condición } (espera hasta que se cumpla). En una Activity, el collect va dentro de una corrutina del lifecycleScope, y por eso no bloquea nada.

Los platform types (String!): la trampa de la interoperabilidad. Cuando Kotlin llama a una API escrita en Java, los tipos de retorno vienen marcados con !: String! significa «esto podría ser nulo, pero Java no lo garantiza, así que Kotlin no te obliga a comprobarlo». Es un platform type: ni String ni String?, sino «el compilador deja de vigilarlo».

La consecuencia práctica: si una API de Java devuelve null y escribes val n: String = api.getNombre(), el compilador no se queja… y el NullPointerException salta en la línea siguiente, cuando ya no sabes de dónde vino. La solución es tipar la API de Java como anulable: val n: String? = api.getNombre(), y comprobar el null con ?. o ?:.

// Clase de JAVA (en un archivo .java): el método puede devolver null
// public class UsuarioJava { public String getNombre() { return null; } }

// Equivalente escrito en Kotlin, para poder probarlo aquí:
class UsuarioJava {
    fun getNombre(): String? = null
}

val usuarioJava = UsuarioJava()

// La forma segura: tipar el resultado como anulable y comprobarlo
val nombre: String? = usuarioJava.getNombre()
val saludo = nombre?.let { "Hola $it" } ?: "Sin nombre"
println(saludo)   // Sin nombre

// Si el método de Java se tipara como String (no anulable) y devolviera null,
// el NPE saltaría en la línea siguiente, sin relación aparente con el origen.

stateIn: un solo flujo compartido entre varias pantallas

Lo anterior escribe el estado a mano en un MutableStateFlow. Cuando la fuente de los datos es un Flow (una base de datos, una API, un Sensor), hay una forma más directa: stateIn convierte ese Flow «frío» en un StateFlow «caliente» y compartido, de modo que dos pantallas que lo miran comparten la misma suscripción.

import kotlinx.coroutines.flow.*
import androidx.lifecycle.ViewModel
import androidx.lifecycle.viewModelScope

// Un repositorio que EXPORTA un Flow, en vez de devolver el dato directamente
class RepositorioProductos {
    private val productos = listOf(
        Producto(1, "Laptop", 1200.0),
        Producto(2, "Ratón", 25.0)
    )
    fun observeProductos(): Flow<List<Producto>> = flow { emit(productos) }
}

class ProductosViewModel(private val repositorio: RepositorioProductos) : ViewModel() {

    // El tipo explícito del 'map' es obligatorio: sin él, el flujo
    // sería de tipo Exito<...> y el 'catch' no podría emitir un Error.
    val uiState: StateFlow<EstadoUI<List<Producto>>> = repositorio.observeProductos()
        .map<List<Producto>, EstadoUI<List<Producto>>> { lista -> EstadoUI.Exito(lista) }
        .catch { error -> emit(EstadoUI.Error(error.message ?: "Error")) }
        .stateIn(
            scope = viewModelScope,
            // Convierte el Flow en un StateFlow que se mantiene vivo
            // 5 segundos después de que nadie lo esté mirando
            started = SharingStarted.WhileSubscribed(5_000),
            initialValue = EstadoUI.Cargando
        )
}
Qué significa SharingStarted.WhileSubscribed(5000). Un StateFlow compartido necesita decidir cuánto tiempo sigue vivo:
  • WhileSubscribed(5000): cuando nadie mira, el flujo se cancela a los 5 segundos. Si alguien vuelve a mirar antes, se reanuda con el último valor, sin repetir la descarga. Es la opción por defecto en la mayoría de apps.
  • Eagerly: el flujo se mantiene activo siempre, aunque nadie mire. Gastas recursos (batería, red) a cambio de tener el dato listo.
  • WhileSubscribed() sin número: se cancela en cuanto nadie lo mira.

Y fíjate en el catch: va antes del stateIn, no después. Si el error lo capturara el StateFlow ya construido, el flujo murió y no volvería a emitir. Por eso el catch transforma el error dentro del flujo, en un EstadoUI.Error que la pantalla sabe pintar.

La Activity consume el estado

El StateFlow del ViewModel es el estado de la pantalla: el Activity se limita a escucharlo y a pintar lo que llega. La conexión se hace con collect, dentro de una corrutina del lifecycleScope.

class MainActivity : AppCompatActivity() {
    private val viewModel: ProductosViewModel by viewModels()

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)

        viewModel.cargarProductos()

        lifecycleScope.launch {
            // Recolecta el estado: se ejecuta cada vez que cambia
            viewModel.uiState.collect { estado ->
                when (estado) {
                    is EstadoUI.Cargando -> mostrarCargando()
                    is EstadoUI.Exito -> mostrarProductos(estado.datos)
                    is EstadoUI.Error -> mostrarError(estado.mensaje)
                }
            }
        }
    }

    private fun mostrarCargando() { /* ... */ }
    private fun mostrarProductos(lista: List<Producto>) { /* ... */ }
    private fun mostrarError(mensaje: String) { /* ... */ }
}
Por qué collect dentro de lifecycleScope.launch. Un collect no termina nunca, así que no puede ejecutarse en el hilo principal de forma directa: lo ejecutas dentro de una corrutina. Y al vivir en el lifecycleScope, esa corrutina se cancela automáticamente cuando la Activity se destruye, de modo que nunca te queda un collect huérfano escribiendo en vistas que ya no existen.

Puente a Compose: el mismo flujo, otro dialecto

Lo que acabas de ver es Compose, solo que con otra sintaxis para pintar. En Compose la pantalla es una función que se vuelve a ejecutar cada vez que cambia un dato; para conservar un valor entre ejecuciones se usa remember + mutableStateOf, y para recolectar el estado del ViewModel se usa collectAsState, que por dentro hace exactamente lo mismo que el collect de arriba.

// La misma idea del collect, pero escrita al estilo Compose
import androidx.compose.material3.*
import androidx.compose.runtime.*
import androidx.lifecycle.compose.collectAsStateWithLifecycle

@Composable
fun PantallaProductos(vm: ProductosViewModel) {
    // 'collectAsState' = el estado actual del StateFlow, ya recogido
    val estado by vm.uiState.collectAsStateWithLifecycle()

    // OJO: 'estado' es una propiedad delegada, y Kotlin no puede hacer
    // 'smart cast' sobre ella. La solucion es copiarla a una val local.
    when (val actual = estado) {
        is EstadoUI.Cargando -> CircularProgressIndicator()
        is EstadoUI.Exito -> Text("Productos: ${actual.datos.size}")
        is EstadoUI.Error -> Text(actual.mensaje)
    }
}

@Composable
fun Contador() {
    // 'remember' guarda el valor entre redibujados de la pantalla
    var contador by remember { mutableStateOf(0) }
    Button(onClick = { contador++ }) { Text("Pulsado $contador veces") }
}
Un detalle que se paga caro en Compose: el smart cast no funciona sobre una propiedad delegada. Cuando escribes val estado by ..., estado es una propiedad delegada, y el compilador no puede garantizar que su valor no cambie entre dos líneas: por eso se niega a hacer is EstadoUI.Exito sobre ella. La solución que verás en todas las guías del módulo es copiar el valor a una variable local dentro del when: when (val actual = estado). Es la misma trampa que con los platform types de Java, y tiene la misma solución: trabaja con una copia local.
El puente mental: remember ≈ una variable normal. En Views guardas el valor en una propiedad de la Activity y lo pinto al actualizar; en Compose lo guardas con remember { mutableStateOf(...) } y el redibujado lo hace el framework por ti. Es el mismo dato con dos envoltorios distintos.
Dos cosas que ya usas y aquí cambian de nombre.
  • collect { } (Views) → collectAsState() / collectAsStateWithLifecycle() (Compose). No cambia el concepto: sigues escuchando un StateFlow.
  • sealed class EstadoUI → en Compose es habitual escribirlo como sealed interface EstadoUI con data object para los casos sin datos. Ambas formas compilan igual y el when sigue siendo exhaustivo; la sealed interface es la que verás en las actividades del módulo.
Lo que no hace esta guía y sí necesitarás después. En las actividades del módulo aparecen dos piezas más que aquí solo se nombran: stateIn (convierte un Flow en un StateFlow que se comparte entre recolectores, con la política SharingStarted que decide cuánto tiempo se mantiene vivo) y ViewModelProvider.Factory (crea el ViewModel con sus dependencias, cuando ya no basta con el viewModels() sin argumentos). Llega con ellas; lo que sí necesitas de esta sección es el flujo mental «el ViewModel publica el estado, la pantalla lo recoge y reacciona».

Función de orden superior con repetición

Crea una función repetirCondicional que reciba un número n y una lambda, y ejecute la lambda mientras n sea mayor que 0, decrementando n en cada iteración.

Crea una var contador = n para poder decrementarla (los parámetros son inmutables) y usa un bucle while. 
fun repetirCondicional(n: Int, accion: (Int) -> Unit) {
    var contador = n
    while (contador > 0) {
        accion(contador)
        contador--
    }
}

fun main() {
    repetirCondicional(5) { println("Iteración: $it") }
}
¿Por qué var contador = n y no n-- directamente? Porque los parámetros de una función son inmutables, igual que un val: Kotlin no te deja reasignarlos. En Java, n-- sobre el parámetro funcionaba sin problema (el parámetro era una variable normal y modificable), así que el reflejo natural al ver Kotlin es pensar «aquí hay que declarar n como var», y eso no es posible. La solución es copiar el valor a una variable local y decrementar la copia. Es el mismo concepto que val vs var, aplicado a un caso con el que te vas a topar.

Sealed class y when

sealed class EstadoDescarga {
    object Iniciada : EstadoDescarga()
    data class Progreso(val porcentaje: Int) : EstadoDescarga()
    data class Completada(val datos: ByteArray) : EstadoDescarga()
    data class Error(val mensaje: String) : EstadoDescarga()
}

fun manejarDescarga(estado: EstadoDescarga) {
    when (estado) {
        EstadoDescarga.Iniciada -> println("Descarga iniciada")
        is EstadoDescarga.Progreso -> println("Progreso: ${estado.porcentaje}%")
        is EstadoDescarga.Completada -> println("Descarga completada: ${estado.datos.size} bytes")
        is EstadoDescarga.Error -> println("Error: ${estado.mensaje}")
    }
}

fun main() {
    manejarDescarga(EstadoDescarga.Iniciada)
    manejarDescarga(EstadoDescarga.Progreso(50))
}
Ojo con ByteArray: una data class compara sus propiedades con ==, pero ByteArray se compara por referencia, no por contenido. Por eso Completada(byteArrayOf(1, 2)) == Completada(byteArrayOf(1, 2)) es false. Si necesitas comparar el contenido, usa .contentEquals().

ViewModel simulado

Simula un ViewModel con un StateFlow que maneje el estado de carga de datos. Crea una función cargarDatos() que emita estados de carga, éxito y error.

Usa un sealed class para estados y MutableStateFlow.
import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

sealed class EstadoDatos {
    object Cargando : EstadoDatos()
    data class Exito(val datos: List<String>) : EstadoDatos()
    data class Error(val mensaje: String) : EstadoDatos()
}

class SimuladorViewModel {
    private val _estado = MutableStateFlow<EstadoDatos>(EstadoDatos.Cargando)
    val estado: StateFlow<EstadoDatos> = _estado.asStateFlow()

    fun cargarDatos() {
        _estado.value = EstadoDatos.Cargando
        try {
            val datos = listOf("Elemento 1", "Elemento 2", "Elemento 3")
            _estado.value = EstadoDatos.Exito(datos)
        } catch (e: Exception) {
            _estado.value = EstadoDatos.Error(e.message ?: "Error desconocido")
        }
    }
}

fun main() = runBlocking {
    val vm = SimuladorViewModel()
    vm.cargarDatos()

    // first() lee el valor ACTUAL del StateFlow y termina.
    // collect() sobre un StateFlow se queda escuchando para siempre:
    // dentro de runBlocking el programa NO terminaría nunca.
    vm.estado.first().let { estado ->
        when (estado) {
            EstadoDatos.Cargando -> println("Cargando...")
            is EstadoDatos.Exito -> println("Datos: ${estado.datos}")
            is EstadoDatos.Error -> println("Error: ${estado.mensaje}")
        }
    }
}

import kotlinx.coroutines.delay

class RepositorioProductos {

    }

    suspend fun aplicarDescuento(categoria: String, porcentaje: Double): List<Producto> {
        delay(500)
        return productos.map {

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*
import androidx.lifecycle.ViewModel

// Estados de la operación (misma sealed class genérica de la sección 3.5)
sealed class EstadoUI<out T> {
    data object Cargando : EstadoUI<Nothing>()
    data class Exito<T>(val datos: T) : EstadoUI<T>()
    data class Error(val mensaje: String) : EstadoUI<Nothing>()
}

// Hereda de ViewModel: así dispone de viewModelScope (se cancela solo al cerrar la pantalla)
class ProductosViewModel : ViewModel() {
    private val repo = RepositorioProductos()
    private val _uiState = MutableStateFlow<EstadoUI<List<Producto>>>(EstadoUI.Cargando)
    val uiState: StateFlow<EstadoUI<List<Producto>>> = _uiState.asStateFlow()

    fun cargarCategoria(categoria: String) {
        viewModelScope.launch {
            _uiState.value = EstadoUI.Cargando
            try {
                val productos = repo.obtenerPorCategoria(categoria)
                _uiState.value = EstadoUI.Exito(productos)
            } catch (e: Exception) {
                _uiState.value = EstadoUI.Error(e.message ?: "Error")
            }
        }
    }
