🧠 Reto de reflexión 0 (calentamiento)

¿Por qué usamos el converter de kotlinx.serialization en lugar de Gson o Moshi?

kotlinx.serialization es nativo de Kotlin: funciona en tiempo de compilación (sin reflexión), entiende data class, nulabilidad y valores por defecto, y es multiplataforma. Además, con ignoreUnknownKeys = true evitamos que un campo nuevo añadido por el servidor rompa el parseo.

Declarar no es conceder. Un permiso «peligroso» (runtime) se declara en el Manifest y además se pide al usuario en ejecución. Sin lo segundo, la API lanza SecurityException. Eso lo resolveremos con una «puerta de permisos» en Compose.

Fase 1: Consumo de API REST con gestión completa de errores (2 h)

▾

Criterios e) y j). Vamos a consumir JSONPlaceholder (https://jsonplaceholder.typicode.com/users), una API pública sin autenticación. El foco no está solo en «que funcione», sino en modelar todos los tipos de fallo posibles.

Los usuarios son ficticios, y eso es lo que queremos. JSONPlaceholder es una API de pruebas: devuelve datos de ejemplo inventados (nombres como «Leanne Graham» y correos como Sincere@april.biz). No hay ningún usuario real detrás, no se pide contraseña y no hay nada que proteger.

De dónde salen los datos, exactamente: no están escritos en tu código. La lista la devuelve el servidor. El recorrido completo es NetworkScreen → UserViewModel.fetchUsers() → safeApiCall { RetrofitClient.api.getUsers() } → GET https://jsonplaceholder.typicode.com/users → el servidor responde con 10 usuarios → kotlinx.serialization los convierte a List<User> → UiState.Success(users) → items(s.users) los pinta en pantalla.

La gracia de usar una API real (aunque sus datos sean inventados) es que te toca el código completo: HTTPS, cabeceras, deserialización, códigos de error y timeouts de verdad. Si los datos estuvieran en tu propio código, todo eso no existiría. Y por eso el mismo JSONPlaceholder te sirve más adelante: cuando hagas el Reto 3 y guardes la lista en DataStore, o cuando la Actividad 3.1 añada tu base de datos local con Room, cambiarás getUsers() por una consulta a tu propia base de datos y la interfaz no cambiará ni una línea.

4.2. Cliente Retrofit con buenas prácticas HTTPS

Archivo nuevo: RetrofitClient.kt

RetrofitClient.kt
package com.example.conectividad

import java.util.concurrent.TimeUnit
import kotlinx.serialization.json.Json
import okhttp3.MediaType.Companion.toMediaType
import okhttp3.OkHttpClient
import okhttp3.logging.HttpLoggingInterceptor
import retrofit2.Retrofit
import retrofit2.converter.kotlinx.serialization.asConverterFactory

object RetrofitClient {
    private const val BASE_URL = "https://jsonplaceholder.typicode.com/"

    // Si el servidor añade campos nuevos, no rompemos el parseo
    private val json = Json { ignoreUnknownKeys = true }

    private val loggingInterceptor = HttpLoggingInterceptor().apply {
        level = HttpLoggingInterceptor.Level.BASIC // En producción: NONE
    }

    private val okHttpClient = OkHttpClient.Builder()
        .addInterceptor(loggingInterceptor)
        .connectTimeout(10, TimeUnit.SECONDS)
        .readTimeout(10, TimeUnit.SECONDS)
        .build()

    val api: ApiService by lazy {
        Retrofit.Builder()
            .baseUrl(BASE_URL) // HTTPS obligatorio en producción
            .client(okHttpClient)
            .addConverterFactory(json.asConverterFactory("application/json".toMediaType()))
            .build()
            .create(ApiService::class.java)
    }
}

4.3. Modelado de errores: más allá de un booleano

Un error de red no es lo mismo que un 404 o que un JSON malformado. Modelarlos como tipos te obliga a manejarlos de forma exhaustiva.

Archivo nuevo: NetworkResult.kt

NetworkResult.kt
package com.example.conectividad

import java.io.IOException
import kotlinx.serialization.SerializationException
import retrofit2.HttpException

sealed interface NetworkResult<out T> {
    data class Success<T>(val data: T) : NetworkResult<T>
    data class HttpError(val code: Int, val message: String) : NetworkResult<Nothing>
    data class NetworkError(val cause: Exception) : NetworkResult<Nothing>
    data class SerializationError(val cause: Exception) : NetworkResult<Nothing>
}

suspend fun <T> safeApiCall(block: suspend () -> T): NetworkResult<T> {
    return try {
        NetworkResult.Success(block())
    } catch (e: HttpException) {          // El servidor respondió 4xx / 5xx
        NetworkResult.HttpError(e.code(), e.message())
    } catch (e: IOException) {            // Sin red, DNS, timeout...
        NetworkResult.NetworkError(e)
    } catch (e: SerializationException) { // El JSON no encaja con el DTO
        NetworkResult.SerializationError(e)
    }
}
¿Por qué no catch (e: Exception)? Porque atraparías también CancellationException (rompiendo la cancelación de corrutinas) y perderías la distinción entre tipos de fallo, que es justo lo que queremos modelar.

4.4. ViewModel con estados claros

UserViewModel.kt
package com.example.conectividad

import androidx.lifecycle.ViewModel
import androidx.lifecycle.viewModelScope
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.launch

sealed interface UiState {
    data object Loading : UiState
    data class Success(val users: List<User>) : UiState
    data class Error(val message: String) : UiState
}

class UserViewModel : ViewModel() {
    private val _uiState = MutableStateFlow<UiState>(UiState.Loading)
    val uiState: StateFlow<UiState> = _uiState.asStateFlow()

    init { fetchUsers() }

    fun fetchUsers() {
        viewModelScope.launch {
            _uiState.value = UiState.Loading
            when (val result = safeApiCall { RetrofitClient.api.getUsers() }) {
                is NetworkResult.Success -> _uiState.value = UiState.Success(result.data)
                is NetworkResult.HttpError -> _uiState.value = UiState.Error("Error del servidor: ${result.code}")
                is NetworkResult.NetworkError -> _uiState.value = UiState.Error("Sin conexión. Revisa tu red.")
                is NetworkResult.SerializationError -> _uiState.value = UiState.Error("Respuesta inesperada del servidor.")
            }
        }
    }
}

5.2. Controlador de Bluetooth: descubrimiento, emparejamiento y envío

Archivo nuevo: BluetoothController.kt. Agrupa las tres operaciones en una clase:

BluetoothController.kt
package com.example.conectividad

import android.Manifest
import android.annotation.SuppressLint
import android.bluetooth.BluetoothAdapter
import android.bluetooth.BluetoothDevice
import android.bluetooth.BluetoothManager
import android.bluetooth.BluetoothSocket
import android.content.BroadcastReceiver
import android.content.Context
import android.content.Intent
import android.content.IntentFilter
import android.content.pm.PackageManager
import android.os.Build
import androidx.core.content.ContextCompat
import androidx.core.content.IntentCompat
import java.io.IOException
import java.util.UUID
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.withContext

@SuppressLint("MissingPermission") // Cada método comprueba el permiso con has(...) antes de usar la API
class BluetoothController(
    private val context: Context,
    private val onDeviceFound: (BluetoothDevice) -> Unit,
    private val onDiscoveryFinished: () -> Unit = {}
) {
    private val adapter: BluetoothAdapter? =
        context.getSystemService(BluetoothManager::class.java)?.adapter

    val isAvailable: Boolean get() = adapter != null
    val isEnabled: Boolean get() = adapter?.isEnabled == true

    private var receiverRegistered = false

    private val receiver = object : BroadcastReceiver() {
        override fun onReceive(ctx: Context, intent: Intent) {
            when (intent.action) {
                BluetoothDevice.ACTION_FOUND -> {
                    val device = IntentCompat.getParcelableExtra(
                        intent, BluetoothDevice.EXTRA_DEVICE, BluetoothDevice::class.java
                    )
                    device?.let(onDeviceFound)
                }
                BluetoothAdapter.ACTION_DISCOVERY_FINISHED -> onDiscoveryFinished()
            }
        }
    }

    // ---------- Permisos ----------
    private fun has(permission: String) =
        ContextCompat.checkSelfPermission(context, permission) == PackageManager.PERMISSION_GRANTED

    private fun canScan() =
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.S) has(Manifest.permission.BLUETOOTH_SCAN)
        else has(Manifest.permission.ACCESS_FINE_LOCATION)

    private fun canConnect() =
        Build.VERSION.SDK_INT < Build.VERSION_CODES.S || has(Manifest.permission.BLUETOOTH_CONNECT)

    // ---------- 1. DESCUBRIR ----------
    fun startDiscovery(): Boolean {
        val bt = adapter ?: return false
        if (!bt.isEnabled || !canScan()) return false

        if (!receiverRegistered) {
            val filter = IntentFilter().apply {
                addAction(BluetoothDevice.ACTION_FOUND)
                addAction(BluetoothAdapter.ACTION_DISCOVERY_FINISHED)
            }
            // ACTION_FOUND lo envía el sistema: el receptor debe estar "exported"
            ContextCompat.registerReceiver(context, receiver, filter, ContextCompat.RECEIVER_EXPORTED)
            receiverRegistered = true
        }
        if (bt.isDiscovering) bt.cancelDiscovery()
        return bt.startDiscovery()
    }

    fun stopDiscovery() {
        if (canScan()) adapter?.cancelDiscovery()
        if (receiverRegistered) {
            context.unregisterReceiver(receiver)
            receiverRegistered = false
        }
    }

    // ---------- 2. EMPAREJAR ----------
    fun pairDevice(device: BluetoothDevice): Boolean {
        if (!canConnect()) return false
        // El sistema muestra su propio diálogo (PIN o confirmación)
        return device.bondState == BluetoothDevice.BOND_NONE && device.createBond()
    }

    fun nameOf(device: BluetoothDevice): String? = if (canConnect()) device.name else null

    // ---------- 3. ENVIAR (RFCOMM) ----------
    suspend fun sendMessage(device: BluetoothDevice, message: String): Result<Unit> =
        withContext(Dispatchers.IO) { // connect() es BLOQUEANTE: nunca en el hilo principal
            if (!canConnect()) {
                return@withContext Result.failure(SecurityException("Falta el permiso BLUETOOTH_CONNECT"))
            }
            var socket: BluetoothSocket? = null
            try {
                // CRÍTICO: cancelar el descubrimiento antes de conectar
                if (canScan()) adapter?.cancelDiscovery()

                socket = device.createRfcommSocketToServiceRecord(SPP_UUID)
                socket.connect() // Bloqueante, pero estamos en Dispatchers.IO

                socket.outputStream.apply {
                    write(message.toByteArray())
                    flush()
                }
                Result.success(Unit)
            } catch (e: IOException) {
                Result.failure(e)
            } finally {
                try { socket?.close() } catch (_: IOException) { }
            }
        }

    companion object {
        /** UUID estándar del Serial Port Profile (SPP) */
        val SPP_UUID: UUID = UUID.fromString("00001101-0000-1000-8000-00805F9B34FB")
    }
}
Importante: startDiscovery() consume muchos recursos. Dura aproximadamente 12 segundos y debes llamar a cancelDiscovery() antes de conectar con un dispositivo, o la conexión será lenta y probablemente falle.
Alternativa moderna: CompanionDeviceManager simplifica el emparejamiento y no requiere permisos de ubicación, pero está pensado para dispositivos *companion* (auriculares, relojes). Para esta práctica, createBond() es suficiente y más directo.

5.3. Notas sobre el emparejamiento y el envío

  • Emparejar: no gestionas el diálogo de PIN; lo muestra el sistema.
  • connect() es bloqueante y la documentación oficial es explícita: no ejecutarlo en el hilo de UI. Por eso sendMessage usa withContext(Dispatchers.IO); con viewModelScope.launch o rememberCoroutineScope() a secas correría en el hilo principal.
  • cancelDiscovery() antes de connect() y socket.close() siempre (en finally).
  • El receptor del escaneo se registra y se desregistra con control (receiverRegistered) para no filtrarlo ni desregistrarlo dos veces.

El UUID 00001101-... es el estándar del Serial Port Profile (SPP). ¿Qué ocurre si el dispositivo remoto no ofrece ese servicio?

createRfcommSocketToServiceRecord(uuid) busca el servicio con ese UUID en el SDP (*Service Discovery Protocol*) del dispositivo remoto. Si no lo encuentra, connect() lanzará una IOException. Para comunicación entre dos instancias de tu app, ambas deben usar el mismo UUID, que puede ser uno generado por ti (no necesariamente el de SPP).

package com.example.conectividad

import android.app.PendingIntent
import android.content.ActivityNotFoundException
import android.content.Context
import android.content.Intent
import android.net.Uri
import android.os.Build
import android.telephony.SmsManager

const val SMS_SENT_ACTION = "com.example.conectividad.SMS_SENT"

/** Envío directo (requiere el permiso SEND_SMS concedido). */
fun sendSms(context: Context, phoneNumber: String, message: String) {
    val smsManager: SmsManager = if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.S) {
        context.getSystemService(SmsManager::class.java)
    } else {
        @Suppress("DEPRECATION")
        SmsManager.getDefault()
    }

    // Un SMS largo se divide en varias partes
    val parts = smsManager.divideMessage(message)

    // PendingIntent para saber si el SMS llegó al centro de mensajes
    val sentIntent = PendingIntent.getBroadcast(
        context, 0,
        Intent(SMS_SENT_ACTION).setPackage(context.packageName),
        PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
    )
    val sentIntents = ArrayList(List(parts.size) { sentIntent })

    smsManager.sendMultipartTextMessage(phoneNumber, null, parts, sentIntents, null)
}

/** Delegar en la app de mensajería del sistema (sin permiso SEND_SMS). */
fun sendSmsViaIntent(context: Context, phoneNumber: String, message: String): Boolean {
    val intent = Intent(Intent.ACTION_SENDTO).apply {
        data = Uri.parse("smsto:$phoneNumber")
        putExtra("sms_body", message)
    }
    return try {
        context.startActivity(intent)
        true
    } catch (e: ActivityNotFoundException) {
        false // No hay ninguna app de SMS instalada
    }
}

¿Qué diferencias hay entre SmsManager e Intent ACTION_SENDTO en términos de UX, permisos y fiabilidad?

SmsManager envía en segundo plano (el usuario no ve la app de mensajería) pero requiere SEND_SMS y puede fallar silenciosamente si no gestionas los callbacks. Intent abre la app de mensajería, el usuario confirma el envío (mayor control), no requiere SEND_SMS, pero depende de que haya una app de SMS instalada y no es «silencioso».

¿Por qué funciona si te lo mandas a ti mismo? Precisamente porque la radio GSM simulada del emulador devuelve el mensaje al mismo dispositivo. El envío se hace de verdad (la llamada a SmsManager sale, con su PendingIntent y todo) y luego el mensaje aparece en la bandeja de entrada como si te lo hubiera mandado otro. Eso es lo que te confirma que el envío funciona. Lo que no te confirma es que tu app sepa recibirlo: de eso va el apartado 6.5.
  • Si prefieres verlo en el log de Android en lugar de en la app de Mensajes: adb logcat -s SmsManager mientras pulsas el botón.
  • En un móvil real con SIM, usa un número válido (cuidado con el coste del SMS).
  • El PendingIntent SMS_SENT_ACTION se dispara, pero nadie lo escucha todavía: eso es el Reto 2.

Cómo simular un SMS entrante de verdad

La forma documentada es el comando de consola del emulador sms send: genera un SMS entrante en ese emulador, como si le llegara de ese número. El atajo adb emu lo ejecuta y vuelve al instante:

6.5. Recibir SMS

Hasta ahora solo has enviado SMS. La otra mitad del criterio es recibirlos: cuando entra un SMS, el sistema difunde un broadcast con la acción android.provider.Telephony.SMS_RECEIVED y toda app que declare el permiso RECEIVE_SMS lo recibe, no solo la app de mensajería del sistema.

Archivo nuevo: SmsReceiver.kt

SmsReceiver.kt
package com.example.conectividad

import android.content.BroadcastReceiver
import android.content.Context
import android.content.Intent
import android.provider.Telephony

/**
 * Receptor de SMS entrantes.
 *
 * Ojo: este objeto lo crea el SISTEMA (por eso lo declaramos en el Manifest),
 * no tu app. Por tanto no puede tocar la UI: solo publica el mensaje en el SmsBus.
 */
class SmsReceiver : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        if (intent.action != Telephony.Sms.Intents.SMS_RECEIVED_ACTION) return

        // Devuelve un array: un SMS largo llega partido en varios trozos
        val parts = Telephony.Sms.Intents.getMessagesFromIntent(intent) ?: return
        if (parts.isEmpty()) return

        // Hay que concatenar el cuerpo: si no, solo se ve la primera parte
        val body = parts.joinToString("") { it.messageBody }
        val sender = parts.firstOrNull()?.originatingAddress ?: "(número desconocido)"

        SmsBus.publish(sender, body)
    }
}

Archivo nuevo: SmsBus.kt. Es el puente entre el receptor (que vive en el framework) y la interfaz (Compose):

SmsBus.kt
package com.example.conectividad

import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.asStateFlow

/** Un SMS que acaba de entrar en el dispositivo. */
data class SmsReceived(val sender: String, val body: String, val id: Long)

/**
 * Puente entre el receptor y la UI.
 *
 * El id no es un detalle: un StateFlow NO vuelve a emitir si el valor nuevo es
 * igual al anterior, así que dos SMS idénticos seguidos (el mismo texto del
 * mismo emisor) se comerían el segundo. Con un id incremental cada aviso es único.
 */
object SmsBus {
    private var nextId = 0L
    private val _received = MutableStateFlow<SmsReceived?>(null)
    val received = _received.asStateFlow()

    fun publish(sender: String, body: String) {
        _received.value = SmsReceived(sender, body, nextId++)
    }
}
¿Por qué un SmsBus y no pintar directamente en el receptor? Porque un receptor declarado en el Manifest lo instancia el sistema, fuera de tu app: no tiene ninguna Activity delante y no puede tocar la UI. La solución estándar es un bus: el receptor publica el dato y la pantalla se suscribe a él.

Preguntas de comprobación

▾

Antes de pasar a los retos, comprueba que lo has entendido. Intenta responder antes de ver la solución.

Pregunta 1 · Excepciones

¿Qué excepción lanza Retrofit cuando el servidor responde 404, y por qué safeApiCall no la trata como un error de red?

Lanza retrofit2.HttpException. No es un error de red porque la comunicación funcionó (el servidor respondió): es un error de aplicación/servidor. Por eso tiene su propia rama (HttpError) separada de IOException (sin conexión, timeout…).
Pregunta 2 · Permisos

¿Por qué BLUETOOTH y BLUETOOTH_ADMIN llevan maxSdkVersion="30" en el Manifest?

Porque solo se usan en Android 11 o inferior. Desde Android 12 los sustituyen BLUETOOTH_SCAN y BLUETOOTH_CONNECT; declararlos sin límite pediría a la app permisos que ya no necesita.
Pregunta 3 · SMS

Un SMS de 200 caracteres con tildes (á, é, í…), ¿cuántas partes necesita?

Las tildes á, í, ó, ú no están en el alfabeto GSM de 7 bits, así que el SMS se codifica en UCS-2: 70 caracteres si cabe en una parte o 67 por parte si se divide. 200 / 67 → 3 partes. (Compruébalo con la calculadora de la sección 6.)
Pregunta 4 · Hilos

¿Por qué no basta con viewModelScope.launch { socket.connect() } para no bloquear la UI?

viewModelScope usa por defecto Dispatchers.Main, así que connect() (bloqueante) se ejecutaría en el hilo principal. Hay que cambiar de contexto con withContext(Dispatchers.IO).
