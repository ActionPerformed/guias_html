Introducción

En la práctica anterior desplegaste un stack LEMP funcional con Nginx, MariaDB y phpMyAdmin. Ese stack servía una página estática y permitía administrar la base de datos desde el navegador.

En esta segunda práctica, vas a transformar ese stack en un gestor de contenidos real: WordPress. Aprenderás a integrarlo en el stack existente, personalizarlo desde la interfaz, activar mecanismos de seguridad y verificar que todo funciona correctamente.

05

Modificaciones en la configuración existente

5.1 · Crear archivo .env para gestionar secretos

En la Práctica 1 las contraseñas estaban en el docker-compose.yml. Es una mala práctica. Vamos a externalizarlas.

Crear archivo: C:\proyectos\mi-proyecto\.env

.env
# Contraseñas de MariaDB
MARIADB_ROOT_PASSWORD=rootpass
MARIADB_DATABASE=mi_app
MARIADB_USER=usuario
MARIADB_PASSWORD=userpass

# Configuración de WordPress
WORDPRESS_DB_NAME=mi_app
WORDPRESS_TABLE_PREFIX=wp_

Docker Compose lee automáticamente este archivo y sustituye las variables ${VARIABLE} en el YAML. Así, las contraseñas no quedan expuestas en el archivo de configuración.

📸
Captura requerida

Captura del archivo .env con los valores configurados.

?

¿Por qué es mala práctica tener las contraseñas directamente en el docker-compose.yml en vez de en un .env?

Solución

Porque el docker-compose.yml suele subirse a un repositorio de control de versiones (Git) y compartirse con el equipo. Si las contraseñas están escritas ahí, quedan expuestas a cualquiera que tenga acceso al repositorio, incluido su historial. El archivo .env se puede excluir del control de versiones (añadiéndolo a .gitignore), de forma que cada persona o entorno tenga sus propios secretos sin que viajen junto al código.

5.2 · Cambio en Nginx: de servidor estático a proxy inverso

Archivo a modificar: C:\proyectos\mi-proyecto\config\nginx\default.conf

nginx · default.conf (nuevo)
server {
    listen 80;
    server_name localhost;
    root /var/www/html;
    index index.php;

    # Permitir subidas de hasta 64MB (temas, plugins, imágenes)
    client_max_body_size 64M;

    # Pasar todas las peticiones a WordPress (permite enlaces permanentes)
    location / {
        try_files $uri $uri/ /index.php?$args;
    }

    # Pasar los archivos .php a PHP-FPM de WordPress
    location ~ \.php$ {
        include fastcgi_params;
        fastcgi_pass wordpress:9000;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
    }

    # Bloquear acceso a archivos sensibles
    location = /wp-config.php { deny all; }
    location = /xmlrpc.php    { deny all; }
    location ~ /\.ht          { deny all; }

    # Bloquear acceso a wp-login.php desde fuera (opcional, descomentar si se necesita)
    # location = /wp-login.php {
    #     allow 192.168.1.0/24;
    #     allow 127.0.0.1;
    #     deny all;
    #     include fastcgi_params;
    #     fastcgi_pass wordpress:9000;
    #     fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
    # }
}

?

¿Qué pasaría si quitaras el bloque location ~ \.php$? ¿Qué vería el navegador al pedir una página de WordPress?

Solución

Nginx seguiría la regla de location /, que intenta servir el archivo con try_files. Como Nginx no sabe interpretar PHP (solo sirve archivos), si el archivo .php existe en disco lo enviaría al navegador como texto plano sin ejecutar (el usuario vería el código fuente de PHP en vez de la página). Sin ese bloque, Nginx no tiene ninguna instrucción para delegar en PHP-FPM, así que WordPress nunca llegaría a ejecutarse.

?

¿Por qué es crítico bloquear el acceso directo a wp-config.php aunque solo esté alojado dentro del contenedor?

Solución

wp-config.php contiene las credenciales de la base de datos (usuario, contraseña, host) y claves secretas de WordPress. El bloqueo en Nginx evita que, ante un fallo de configuración de PHP-FPM o un error de interpretación, ese archivo se sirva como texto plano al navegador, exponiendo las credenciales a cualquiera que conozca la URL. Es una capa adicional de defensa, no una confianza ciega en que PHP-FPM siempre funcionará como se espera.

5.5 · Añadir secretos y healthcheck a MariaDB

yaml
mariadb:
  image: mariadb:10.11
  container_name: mi-mariadb
  environment:
    MARIADB_ROOT_PASSWORD: ${MARIADB_ROOT_PASSWORD}
    MARIADB_DATABASE: ${MARIADB_DATABASE}
    MARIADB_USER: ${MARIADB_USER}
    MARIADB_PASSWORD: ${MARIADB_PASSWORD}
  volumes:
    - mariadb_data:/var/lib/mysql
  networks:
    - mi-red
  healthcheck:
    test: ["CMD", "healthcheck.sh", "--connect", "--innodb_initialized"]
    interval: 10s
    timeout: 5s
    retries: 5
  restart: unless-stopped

El healthcheck ejecuta un script dentro del contenedor que verifica si MariaDB está realmente lista para aceptar conexiones, no solo arrancada. Esto evita el error clásico de «WordPress no conecta con la base de datos» en el primer arranque.

6.1 · Servicio WordPress

yaml

Nota sobre PHP-FPM

La imagen wordpress:6-php8.3-fpm no incluye servidor web. Solo procesa PHP. Nginx actúa como proxy inverso: recibe las peticiones HTTP, las pasa a PHP-FPM (puerto 9000) y devuelve la respuesta.

📸
Captura requerida

Captura del servicio wordpress completo.

?

Esta imagen de WordPress no sirve directamente si accedes a su puerto desde fuera. ¿Qué le falta y quién completa esa función?

Solución

Le falta un servidor web que hable HTTP con el navegador. La variante -fpm de la imagen solo ejecuta PHP-FPM, que escucha en el puerto 9000 con el protocolo FastCGI — no HTTP. Por eso no se publica ningún puerto del contenedor wordpress hacia el host: es Nginx quien recibe las peticiones HTTP del navegador en el puerto 80/8080 y las traduce a FastCGI contra wordpress:9000.

?

¿Qué diferencia real hay entre depends_on: - mariadb (Práctica 1) y depends_on: mariadb: condition: service_healthy (Práctica 2)?

Solución

La forma simple (- mariadb) solo garantiza el orden de arranque de los contenedores: Docker inicia el contenedor de MariaDB antes que el de WordPress, pero no espera a que el proceso de MariaDB esté realmente aceptando conexiones — el contenedor puede estar "arrancado" mientras MariaDB todavía está inicializando sus tablas internamente. La forma con condition: service_healthy obliga a Docker Compose a esperar a que el healthcheck de MariaDB informe healthy antes de arrancar WordPress, evitando el error de conexión en el primer arranque.

?

Has configurado client_max_body_size 64M en Nginx. ¿Qué pasaría si subieras un archivo de 70 MB? ¿Dónde se rechaza, en Nginx o en WordPress?

Solución

Nginx rechazaría la petición antes de que llegara a WordPress, devolviendo un error 413 (Request Entity Too Large). La petición nunca alcanza PHP-FPM: Nginx corta la subida en cuanto el cuerpo de la petición supera el límite configurado. Por eso este límite debe coordinarse con los límites internos de PHP (upload_max_filesize, post_max_size) si se quiere subir archivos grandes de verdad — el más restrictivo de todos gana.

?

¿Por qué activar el límite de intentos de login es una medida de seguridad importante en un WordPress público?

Solución

Sin límite, un atacante puede lanzar un ataque de fuerza bruta: probar miles de combinaciones de usuario/contraseña de forma automatizada contra wp-login.php hasta acertar. Limitar los intentos fallidos (y bloquear temporalmente la IP o la cuenta tras varios fallos) convierte ese ataque en impracticable en un tiempo razonable, sin afectar a un usuario legítimo que simplemente se equivoca una o dos veces.

?

¿Por qué crear un usuario con rol Colaborador en vez de dar acceso de Administrador a todo el mundo?

Solución

Es la aplicación directa del principio de mínimo privilegio: un Colaborador puede escribir y editar sus propias entradas, pero no publicarlas directamente, ni instalar plugins, ni cambiar la configuración del sitio, ni gestionar otros usuarios. Si esa cuenta se ve comprometida (contraseña filtrada, sesión robada), el daño posible queda limitado a lo que ese rol puede hacer — muy lejos del control total que tendría una cuenta de Administrador.

?

En la prueba 10.7, la entrada sobrevive a docker compose down. Ahora hay dos sitios donde vive información de WordPress — ¿cuáles son y qué guarda cada uno?

Solución

El volumen mariadb_data guarda el contenido de la entrada (título, texto, metadatos) en las tablas de la base de datos, como wp_posts. El volumen wordpress_data guarda los archivos de WordPress: el núcleo, los temas, los plugins y los archivos subidos a la biblioteca de medios (imágenes, documentos). Un down simple conserva ambos; un down --volumes los borraría a los dos.

11.1 · Verificar la accesibilidad desde otro dispositivo

powershell
ipconfig

Busca la dirección IPv4. Desde otro dispositivo (móvil, otro PC), accede a http://[IP-DE-TU-PC]:8080.

Problema común

WordPress guarda la URL del sitio en la base de datos. Si accedes desde otra IP, WordPress redirige a localhost:8080, rompiendo la navegación. Para solucionarlo, edita wp-config.php o usa phpMyAdmin:

sql
UPDATE wp_options SET option_value = 'http://[IP-DE-TU-PC]:8080' WHERE option_name IN ('siteurl', 'home');
📸
Captura requerida

Captura desde otro dispositivo mostrando el sitio accesible.

?

¿Por qué WordPress guarda la URL del sitio en la base de datos en vez de leerla dinámicamente de la petición del navegador?

Solución

WordPress usa siteurl y home para construir enlaces absolutos en todo el sitio (menús, enlaces internos, URLs de recursos, redirecciones tras el login). Guardarlos de forma fija evita inconsistencias y ataques de manipulación de cabeceras (un atacante podría falsificar la cabecera Host de una petición para intentar generar enlaces maliciosos si WordPress confiara ciegamente en lo que dice el navegador). El coste es justamente el que has visto: si cambias cómo accedes al sitio, hay que actualizar también ese valor guardado.

Retos para alumnado avanzado

  1. Crear una imagen personalizada de WordPress: añade extensiones PHP que falten (por ejemplo, gd) creando un Dockerfile que extienda la imagen oficial.
  2. Añadir HTTPS: configura un certificado autofirmado o Let's Encrypt para servir el sitio por HTTPS.
  3. Bloquear wp-login.php por IP: descomenta el bloque en default.conf y limita el acceso al panel de administración.
  4. Instalar WP-CLI: usa la variante wordpress:cli para gestionar WordPress desde línea de comandos.
