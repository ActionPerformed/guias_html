01

Introducción

Esta guía práctica te llevará a desplegar un stack LEMP completo usando Docker: un servidor web Nginx, una base de datos MariaDB y un panel de administración phpMyAdmin. Todo ello orquestado con Docker Compose.

Se trabajará sobre lso conceptos desarrollados en la Unidad de Trabajo 1. Si algo no te suena (qué es un volumen, qué diferencia hay entre cliente y servidor, qué es un proxy inverso), consulta la guía teórica de la unidad antes de continuar.

El objetivo es que, al terminar, no solo tengas el stack funcionando sino que también hayas comprobado su comportamiento bajo carga, aplicado mecanismos de control de acceso y sepas cómo apagarlo limpiamente (con y sin borrado de datos).

02

Objetivos de aprendizaje

  • Preparar un entorno de trabajo con Docker en Windows 11.
  • Definir un stack multi-contenedor con Docker Compose.
  • Configurar Nginx como servidor web sirviendo contenido estático.
  • Desplegar MariaDB con persistencia de datos mediante volúmenes.
  • Integrar phpMyAdmin para administrar la base de datos desde el navegador.
  • Verificar el correcto funcionamiento de cada componente.
  • Ejecutar pruebas de carga con ApacheBench e interpretar los resultados.
  • Aplicar mecanismos de gestión de acceso (autenticación básica, restricción por IP).
  • Diferenciar entre apagar el stack conservando datos y borrarlos definitivamente.
  • Diagnosticar y resolver problemas frecuentes.
03

Prerrequisitos

Antes de empezar, asegúrate de que tienes:

  • Windows 11 con Docker instalado y funcionando.
  • Una terminal (PowerShell o Windows Terminal).
  • Un editor de texto (VS Code, Notepad++...).

Verificación rápida de Docker

powershell
docker --version
docker compose version

Ambos comandos deben devolver una versión. Si alguno falla, revisa la instalación de Docker antes de continuar.

Paso 2 · Verificar recursos asignados a Docker

Docker Desktop permite limitar la CPU, RAM y disco que puede usar el motor de Docker. Para esta práctica, con 2 GB de RAM y 2 CPU es suficiente. Puedes comprobarlo en Docker Desktop → Settings → Resources.

Paso 3 · Verificar que los puertos están libres

Vamos a usar los puertos 8080 (Nginx) y 8081 (phpMyAdmin).

powershell
netstat -ano | findstr :8080
netstat -ano | findstr :8081

Si no devuelven nada, están libres. Si devuelven algo, cambia el puerto en el docker-compose.yml más adelante.

05

Arquitectura del stack a desplegar

En esta práctica, desplegaremos la siguiente arquitectura, con los contenedores de Nginx y MariaDB-phpMyAdmin no conectados.

En siguientes prácticas, añadiremos el módulo de PHP-FRM para poder atacar la base de datos desde Nginx.

  • Nginx sirve la página estática en localhost:8080.
  • phpMyAdmin se conecta a MariaDB por nombre de servicio (mariadb) y se expone en localhost:8081.
  • MariaDB guarda sus datos en el volumen mariadb_data.
  • PHP-FPM actuaría como puente de acceso entre Nginx y MariaDB (no lo instalaremos en esta práctica).
  • Los cuatro contenedores comparten la red mi-red, lo que permite que se resuelvan por nombre.
06

Creación del stack paso a paso con Docker Compose

Paso 1 · Crear docker-compose.yml

yaml
services:
  nginx:
    image: nginx:alpine
    container_name: mi-nginx
    ports:
      - "8080:80"
    volumes:
      - ./config/nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
      - ./html:/usr/share/nginx/html:ro
    networks:
      - mi-red
    restart: unless-stopped

  mariadb:
    image: mariadb:10.11
    container_name: mi-mariadb
    environment:
      MARIADB_ROOT_PASSWORD: rootpass
      MARIADB_DATABASE: mi_app
      MARIADB_USER: usuario
      MARIADB_PASSWORD: userpass
    volumes:
      - mariadb_data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "healthcheck.sh", "--connect", "--innodb_initialized"]
      interval: 10s
      timeout: 5s
      retries: 5
    networks:
      - mi-red
    restart: unless-stopped

  phpmyadmin:
    image: phpmyadmin/phpmyadmin
    container_name: mi-phpmyadmin
    ports:
      - "8081:80"
    environment:
      PMA_HOST: mariadb
    depends_on:
      mariadb:
        condition: service_healthy
    networks:
      - mi-red
    restart: unless-stopped

volumes:
  mariadb_data:

networks:
  mi-red:
Atención

Las contraseñas rootpass, userpass son de ejemplo. En producción usa contraseñas robustas y gestiónalas con variables de entorno o secretos.

Pruebas de carga

Una vez verificado que el stack funciona, vamos a someterlo a estrés para entender sus límites.

¿Qué es una prueba de carga?

MétricaQué indica
Tiempo de respuestaCuánto tarda el servidor en devolver una página
ThroughputPeticiones por segundo que procesa
Tasa de erroresPeticiones que fallan bajo presión
Uso de recursosCPU, RAM y disco durante la prueba

Actividad 8.1 · Prueba básica con ApacheBench

Paso 1 — Instalar ab dentro del contenedor de Nginx

powershell
docker exec -it mi-nginx sh
apk add --no-cache apache2-utils

Paso 2 — Ejecutar la prueba

sh
ab -n 1000 -c 10 http://localhost/
  • -n 1000: 1000 peticiones totales.
  • -c 10: 10 usuarios concurrentes.

Paso 3 — Interpretar los resultados

  • Requests per second: throughput del servidor.
  • Time per request: tiempo medio por petición.
  • Failed requests: si hay errores, algo va mal.
  • Transfer rate: velocidad de transferencia.

Paso 4 — Variar la concurrencia

sh
ab -n 1000 -c 1 http://localhost/
ab -n 1000 -c 50 http://localhost/
ab -n 1000 -c 200 http://localhost/
Simulador · efecto de la concurrencia (ilustrativo, no son datos reales de tu equipo)

Mueve el deslizador para explorar cómo tienden a comportarse throughput, latencia y errores al aumentar la concurrencia con ab — la forma de las curvas es real, los valores concretos dependen de tu hardware.

Instalación integrada

Cuando trabajas con contenedores, la «instalación» se hace de dos formas: dentro del contenedor (con el gestor de paquetes de la imagen: apk en Alpine, apt en Debian) o en el anfitrión (winget en Windows, apt en Linux).

10

Gestión de acceso aplicada

Vamos a aplicar dos mecanismos de control de acceso en Nginx y uno en MariaDB.

Actividad 10.1 · Autenticación básica HTTP en Nginx

powershell
docker exec -it mi-nginx sh
apk add --no-cache apache2-utils
htpasswd -c /etc/nginx/.htpasswd admin

Introduce la contraseña cuando se solicite.

nginx
server {
    listen 80;
    server_name localhost;

    location / {
        root /usr/share/nginx/html;
        index index.html;
        try_files $uri $uri/ =404;
    }

    location /protegido/ {
        auth_basic "Área restringida";
        auth_basic_user_file /etc/nginx/.htpasswd;

        root /usr/share/nginx/html;
    }
}

Crea una carpeta protegido con un index.html dentro y añade el montaje al docker-compose.yml:

yaml
volumes:
  - ./config/nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
  - ./index.html:/usr/share/nginx/html/index.html:ro
  - ./protegido:/usr/share/nginx/html/protegido:ro
powershell
docker compose up -d
docker exec mi-nginx nginx -s reload

Accede a http://localhost:8080/protegido/. El navegador debe pedir credenciales.

Actividad 10.2 · Restricción por IP

nginx
location /admin/ {
    allow 192.168.1.0/24;
    allow 127.0.0.1;
    deny all;

    root /usr/share/nginx/html;
}

Recarga Nginx y prueba el acceso.

13

Actividades enriquecedoras

Bloque 1 · Persistencia

  • 1.1 — Crea un registro en phpMyAdmin, haz down, vuelve a levantar y comprueba que sigue ahí.
  • 1.2 — Repite el ejercicio con down --volumes y comprueba que los datos desaparecen.

Bloque 2 · Red interna

  • 2.1 — Entra en mi-nginx y haz ping mariadb y ping phpmyadmin.
  • 2.2 — Para MariaDB con docker stop mi-mariadb, comprueba que phpMyAdmin falla, y arráncala de nuevo.

Bloque 3 · Inspección

  • 3.1 — Ejecuta docker compose logs -f nginx y observa en tiempo real mientras accedes a la web.
  • 3.2 — Usa docker inspect para ver la red y los volúmenes de cada contenedor.

Bloque 4 · Modificación en caliente

  • 4.1 — Edita index.html, refresca el navegador y comprueba que el cambio se ve sin reiniciar nada.
  • 4.2 — Edita default.conf, recarga Nginx con nginx -s reload y comprueba el cambio.

Bloque 5 · Averiguar el «por qué»

  • 5.1 — Cambia el mapeo de puertos de Nginx a 9090:80 y comprueba que localhost:8080 deja de funcionar.
  • 5.2 — Cambia MARIADB_ROOT_PASSWORD en el YAML, levanta el stack y comprueba que phpMyAdmin falla si el volumen ya existía.
14

Retos para alumnado avanzado

  1. Conectar con un cliente SQL externo: expón el puerto 3306 de MariaDB y conéctate con DBeaver o HeidiSQL desde Windows.
  2. Dos instancias del stack: levanta dos copias del stack con puertos distintos y comprueba que coexisten.
  3. Migrar a docker run: reproduce el stack sin Docker Compose, usando solo docker network create, docker volume create y docker run.
  4. Añadir HTTPS: genera un certificado autofirmado y configura Nginx para servir por HTTPS.
  5. Monitorización: instala ctop o usa docker stats para registrar el uso de recursos durante una prueba de carga.

Conexión con la Práctica 2 (WordPress)

Esta práctica sienta las bases para una segunda en la que se añadirá WordPress. La progresión prevista:

  1. Añadir un servicio wordpress al docker-compose.yml, conectado a la misma red y a MariaDB.
  2. Modificar la configuración de Nginx para que actúe como proxy inverso hacia WordPress (proxy_pass http://wordpress;).
  3. Mantener phpMyAdmin como herramienta de administración de la base de datos de WordPress.

Todo lo aprendido aquí (redes, volúmenes, variables de entorno, depuración con logs, gestión de acceso) se reutilizará directamente, permitiendo centrarse en los conceptos nuevos (proxy inverso, PHP-FPM, WordPress) sin arrastrar dudas anteriores.
