§1

Introducción

Cuando accedemos a una aplicación web, detrás hay una infraestructura compleja que combina varios componentes: un servidor web que recibe las peticiones, un intérprete de lenguaje que ejecuta el código, una base de datos que almacena la información y un sistema operativo que lo sustenta todo. Entender cómo encajan estas piezas es fundamental para cualquier administrador de sistemas.

Esta guía teórica acompaña a la práctica de despliegue de un stack LEMP con Docker. Los conceptos que aquí se explican, después se aplicarán. El objetivo es que, al acabar esta Unidad de Trabajo, te familiarices con los principales componentes de un stack web.

§2

Objetivos de aprendizaje

  • Identificar los componentes de un stack web y explicar la función de cada uno.
  • Analizar los requerimientos técnicos de una aplicación web antes de desplegarla.
  • Diferenciar los tipos de servidores de aplicaciones y elegir el más adecuado según el caso.
  • Distinguir entre lenguajes de script de cliente y de servidor, y entender cómo interactúan.
  • Describir la arquitectura de un stack LEMP y justificar cada elección tecnológica.
  • Explicar qué son los módulos y componentes de un servidor web y cómo se configuran.
  • Comprender los mecanismos de gestión de acceso: autenticación, autorización y permisos.
  • Identificar prácticas básicas de seguridad en el despliegue de aplicaciones web.
§3

Prerrequisitos

Para aprovechar esta guía es necesario disponer de:

  • Conocimientos básicos de redes: direcciones IP, puertos, protocolo HTTP.
  • Nociones básicas de SQL y bases de datos relacionales.
  • Conceptos elementales de HTML y CSS.
§4

Análisis de requerimientos

Antes de desplegar cualquier aplicación web, lo primero es analizar qué necesita. Este paso, que a menudo se salta, es el que evita problemas posteriores: elegir mal el servidor, dimensionar mal los recursos o ignorar requisitos de seguridad puede arruinar un despliegue.

Tipos de requerimientos

TipoQué incluyeEjemplo
FuncionalesQué debe hacer la aplicación«Los usuarios deben poder registrarse y hacer login»
TécnicosCon qué debe funcionar«PHP 8.2 o superior, MariaDB 10.6+, Nginx 1.24+»
De infraestructuraRecursos necesariosCPU, RAM, disco, ancho de banda
De redPuertos, protocolos, firewall«Abrir 80 y 443, cerrar el resto»
De seguridadProtección de datos y accesos«HTTPS obligatorio, contraseñas hasheadas»
De escalabilidadCómo debe crecer«Debe soportar 1000 usuarios concurrentes»
Nota

En la siguiente práctica trabajarás con contenedores en tu equipo local. Los recursos del anfitrión (tu PC) son los que limitan. Docker Desktop permite asignar CPU y RAM al motor de Docker, pero no puede dar más de lo que tiene el equipo físico.

Elección de tecnologías

Cada decisión técnica tiene implicaciones. Algunos criterios para elegir:

  • Servidor web: Nginx es más eficiente para contenido estático y proxy inverso; Apache es más flexible con .htaccess y módulos dinámicos; Caddy simplifica HTTPS automático.
  • Base de datos: MariaDB y MySQL se integran en el ecosistema web por su sencillez y omnipresencia (Wordpress, Magento, Laravel...); PostgreSQL es más potente en tipos avanzados; SQLite es ligero pero no apto para concurrencia alta.
  • Lenguaje de servidor: PHP es el estándar de facto en hosting compartido; Python y Node.js son más comunes en aplicaciones modernas; Java es habitual en entornos empresariales.

Imagina que tienes que desplegar una tienda online pequeña (menos de 100 productos, tráfico moderado). ¿Qué requerimientos técnicos, de infraestructura y de seguridad establecerías antes de empezar? Justifica cada decisión.

§5

Tipos de servidores de aplicaciones

Un servidor de aplicaciones es el software que recibe peticiones HTTP y devuelve respuestas. Pero no todos los servidores son iguales: algunos sirven solo contenido estático, otros ejecutan código, otros actúan como intermediarios.

Clasificación

TipoFunción principalEjemplos
Servidor web puroSirve archivos estáticos (HTML, CSS, JS, imágenes)Nginx, Apache (modo estático), Lighttpd
Servidor de aplicacionesEjecuta código de servidor y genera respuestas dinámicasTomcat, WildFly, Node.js, Gunicorn
Proxy inversoRecibe peticiones y las redirige a otros servicios internosNginx, HAProxy, Traefik
Balanceador de cargaDistribuye peticiones entre varios servidoresNginx, HAProxy, AWS ELB
Servidor completoCombina todo lo anteriorApache con módulos, IIS

¿Por qué Nginx en esta práctica?

Nginx se ha convertido en el estándar de facto para servidores web modernos por varias razones:

  • Rendimiento: su modelo asíncrono maneja miles de conexiones concurrentes con muy poca memoria.
  • Versatilidad: sirve contenido estático, actúa como proxy inverso, balancea carga y cachea respuestas.
  • Ecosistema: imágenes Docker oficiales, documentación abundante, comunidad enorme.
  • Uso profesional: presente en la mayoría de stacks modernos (LEMP, MEAN, JAMstack).

Si tuvieras que desplegar una aplicación Java empresarial, ¿elegirías Nginx como servidor principal? ¿Por qué? ¿Qué papel jugaría Tomcat en ese escenario?

§6

Lenguajes de script en cliente y servidor

Una aplicación web moderna combina código que se ejecuta en dos lugares distintos: el navegador del usuario (cliente) y el servidor. Entender esta separación es clave para comprender cómo funciona cualquier aplicación web.

Código de cliente

Se ejecuta en el navegador del usuario. El servidor solo lo envía; no lo procesa.

LenguajeFunciónEjemplo
HTMLEstructura del contenido<h1>Título</h1>
CSSPresentación visualbody { font-family: sans-serif; }
JavaScriptInteractividad, lógica en el navegadorgetElementById("btn").addEventListener(...)
TypeScriptJavaScript con tipos (se compila a JS)const nombre: string = "Ana";
WebAssemblyCódigo compilado de alto rendimientoMódulos de cifrado, juegos

El servidor web (Nginx, Apache) simplemente entrega estos archivos al navegador. No los ejecuta.

Código de servidor

Se ejecuta en el servidor antes de enviar la respuesta al cliente. El usuario nunca ve este código, solo el resultado.

LenguajeEntorno típicoCaso de uso
PHPPHP-FPM + Nginx/ApacheWordPress, aplicaciones web clásicas
PythonGunicorn/uWSGI + NginxDjango, Flask, APIs
Node.jsNode + Nginx (proxy)APIs REST, aplicaciones en tiempo real
JavaTomcat/WildFlyAplicaciones empresariales
RubyPuma + NginxRuby on Rails
C#IIS / .NETAplicaciones Microsoft

¿Cómo interactúan cliente y servidor?

  1. El usuario escribe una URL o hace clic en un enlace.
  2. El navegador envía una petición HTTP al servidor.
  3. El servidor ejecuta el código de servidor (si procede).
  4. El servidor devuelve HTML, CSS y JS al navegador.
  5. El navegador renderiza la página y ejecuta el JavaScript de cliente.
  6. Si hay interacción (AJAX, fetch), el ciclo se repite sin recargar la página.

El caso de PHP en un stack LEMP

PHP es un lenguaje de servidor. Para que Nginx pueda ejecutar PHP, necesita un componente intermedio: PHP-FPM (FastCGI Process Manager). El flujo es:

flujo
Navegador → Nginx → PHP-FPM → (ejecuta PHP) → Nginx → Navegador

Nginx recibe la petición, detecta que es un archivo .php, y se la pasa a PHP-FPM mediante el protocolo FastCGI. PHP-FPM ejecuta el código y devuelve el resultado a Nginx, que lo envía al navegador.

Nota para la práctica

En la primera práctica no hay PHP propio que ejecutar, por eso no se instala PHP-FPM. phpMyAdmin trae su propio intérprete PHP interno. En la segunda práctica, al añadir WordPress, PHP-FPM será imprescindible.

¿Por qué crees que el código de cliente (JavaScript) se puede ver con «Ver código fuente» pero el de servidor (PHP) no? ¿Qué implicaciones tiene esto para la seguridad?

§7

Arquitectura de un stack LEMP

Un stack es un conjunto de tecnologías que trabajan juntas para servir una aplicación web. El más común es el LEMP:

LetraTecnologíaFunción
LLinuxSistema operativo base
ENginx (Engine-X)Servidor web / proxy inverso
MMariaDB (o MySQL)Base de datos
PPHPLenguaje de servidor

Otros stacks habituales

Linux + Apache + MySQL + PHP

Hosting compartido, WordPress.

Linux + Nginx + MariaDB + PHP

Aplicaciones modernas, alto rendimiento.

MongoDB + Express + Angular + Node

Aplicaciones JavaScript full-stack.

MongoDB + Express + React + Node

Como MEAN pero con React.

JavaScript + APIs + Markup

Sitios estáticos modernos.

Diagrama de un stack LEMP y flujo de una petición

Esta es la demo central de la guía: elige si el navegador pide un recurso estático o dinámico y sigue el recorrido de la petición.

Simulador · ciclo de vida de una petición HTTP
$ listo — elige el tipo de recurso y pulsa «Enviar petición»
  1. El navegador envía una petición HTTP a Nginx.
  2. Nginx comprueba si el recurso es estático (imagen, CSS) o dinámico (.php).
  3. Si es estático, lo sirve directamente.
  4. Si es dinámico, pasa la petición a PHP-FPM.
  5. PHP-FPM ejecuta el código PHP, que consulta MariaDB si es necesario.
  6. PHP-FPM devuelve el HTML generado a Nginx.
  7. Nginx envía la respuesta al navegador.

¿Por qué Docker para montar un LEMP?

Tradicionalmente, un LEMP se montaba instalando cada componente directamente en el sistema operativo (con apt, yum, etc.). Docker aporta ventajas:

  • Aislamiento: cada servicio en su propio contenedor, sin conflictos de versiones.
  • Reproducibilidad: el mismo stack funciona igual en cualquier equipo.
  • Portabilidad: se puede mover de un servidor a otro sin reinstalar nada.
  • Facilidad de limpieza: se borra el contenedor y no queda rastro.

¿Qué ventajas e inconvenientes tiene montar un LEMP con Docker frente a instalarlo directamente sobre el sistema operativo? Piensa en rendimiento, seguridad y facilidad de mantenimiento.

¿Por qué es importante conocer los módulos?

Porque determinan qué puede hacer tu servidor. Si por ejemplo necesitas HTTPS y Nginx no tiene ngx_http_ssl_module, no funcionará. Así, conocer los módulos te permite:

  • Diagnosticar por qué algo no funciona.
  • Saber qué puedes activar sin reinstalar.
  • Elegir la imagen Docker adecuada (algunas traen módulos extra).

Si quisieras servir una aplicación WordPress con imágenes redimensionadas automáticamente, ¿qué módulos de Nginx y qué extensiones de PHP necesitarías como mínimo?

§9

Gestión de acceso: conceptos

La gestión de acceso es el conjunto de mecanismos que controlan quién puede hacer qué en un sistema. En el contexto de un servidor web y una base de datos, abarca tres conceptos fundamentales: autenticación, autorización y auditoría.

Autenticación — verifica quién eres

MétodoDescripciónUso típico
Usuario y contraseñaCredenciales clásicasPaneles de administración
Autenticación básica HTTPUsuario/contraseña en cabecera HTTPProtección simple de directorios
TokensCadenas temporalesAPIs
CertificadosClave pública/privadaComunicaciones seguras
OAuth / OpenIDDelegación a tercerosLogin con Google, GitHub
MFASegundo factor (TOTP, SMS)Acceso a sistemas críticos

Autorización — determina qué puedes hacer

ModeloDescripciónEjemplo
ACLPermisos por recurso y usuarioArchivos del sistema
Roles (RBAC)Permisos agrupados en rolesUsuario, editor, administrador
Permisos por IPRestricción según origenallow / deny en Nginx
Permisos granularesPor tabla, columna o filaGRANT SELECT ON tabla en MariaDB

Auditoría — registra qué se ha hecho

  • Logs de acceso de Nginx (access.log).
  • Logs de error de Nginx (error.log).
  • Logs de MariaDB (general_log, slow_query_log).
  • Logs del sistema (syslog, journalctl).

Gestión de acceso en Nginx

Nginx ofrece dos mecanismos principales:

Autenticación básica HTTP

nginx
location /protegido/ {
    auth_basic "Área restringida";
    auth_basic_user_file /etc/nginx/.htpasswd;
}

Restricción por IP

nginx
location /admin/ {
    allow 192.168.1.0/24;
    deny all;
}

Ambos pueden combinarse con la directiva satisfy.

Gestión de acceso en MariaDB

MariaDB tiene su propio sistema de usuarios y permisos, independiente del sistema operativo.

sql
CREATE USER 'app_user'@'localhost' IDENTIFIED BY 'contraseña_segura';
sql
GRANT SELECT, INSERT, UPDATE, DELETE ON mi_app.* TO 'app_user'@'localhost';
sql
SHOW GRANTS FOR 'app_user'@'localhost';
sql
REVOKE DELETE ON mi_app.* FROM 'app_user'@'localhost';

Principio de mínimo privilegio

El principio de mínimo privilegio establece que cada usuario o servicio debe tener solo los permisos estrictamente necesarios para realizar su función. Aplicado a un stack web:

  • La aplicación no debe conectarse como root a la base de datos.
  • El usuario de la aplicación solo debe tener permisos sobre su base de datos.
  • Nginx debe ejecutarse con un usuario sin privilegios (www-data, nginx).
  • Los contenedores no deben ejecutarse como root si no es imprescindible.

¿Por qué es peligroso que una aplicación WordPress se conecte a MariaDB con el usuario root? ¿Qué podría pasar si un atacante consigue las credenciales?

§10

Seguridad básica en servidores web

La seguridad no es un añadido: es parte del diseño. Estos son los aspectos básicos que todo administrador debe considerar.

Superficie de ataque

La superficie de ataque es el conjunto de puntos por los que un atacante podría intentar entrar. Cuanto menor sea, mejor.

  • Puertos abiertos: solo los necesarios (80, 443). Cerrar el resto.
  • Servicios expuestos: no exponer MariaDB a internet si no es imprescindible.
  • Versiones desactualizadas: mantener imágenes y paquetes al día.
  • Credenciales débiles: usar contraseñas robustas y únicas.
  • Información filtrada: no mostrar versiones en cabeceras HTTP.

Buenas prácticas

PrácticaPor qué
Usar HTTPSCifra el tráfico; evita interceptación
Contraseñas robustasEvita fuerza bruta
Usuario no root para la appLimita daños si hay brecha
Red interna para BDEvita exposición innecesaria
Logs activadosPermite detectar incidentes
Copias de seguridadPermite recuperarse de fallos
Actualizaciones periódicasCierra vulnerabilidades conocidas

Cabeceras de seguridad HTTP

Nginx puede añadir cabeceras que mejoran la seguridad del navegador:

nginx
add_header X-Frame-Options "SAMEORIGIN";
add_header X-Content-Type-Options "nosniff";
add_header X-XSS-Protection "1; mode=block";
add_header Strict-Transport-Security "max-age=31536000" always;

Contenedores y seguridad

  • No ejecutar como root: usar USER en el Dockerfile o --user en docker run.
  • Imágenes oficiales: evitar imágenes de fuentes desconocidas.
  • Imágenes minimalistas: Alpine reduce la superficie de ataque.
  • Redes aisladas: cada stack en su propia red.
  • Volúmenes de solo lectura: montar configuraciones con :ro.
