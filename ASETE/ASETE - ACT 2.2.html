🎯 ¿Qué vas a construir?

Sobre la MiniApp de Biblioteca que ya funciona, vas a aplicar tres capas de "profesionalización":

  • Namespaces y autoloading: las clases dejan de estar sueltas en el espacio global y pasan a vivir bajo App\. Composer las carga automáticamente. Desaparecen los require_once manuales.
  • Gestión de excepciones: donde antes había exit() o return false, ahora hay throw new ExcepcionPropia(...). Los errores se capturan en un punto central y se muestran con un mensaje amigable.
  • Buenas prácticas: declare(strict_types=1), tipos en todo, PSR-12, nombres coherentes.

Escenario: el equipo de desarrollo de la biblioteca ha crecido. Ya no eres tú solo con tres archivos: hay más gente tocando el código y hay que poner orden. El primer paso antes de migrar a un framework es que el proyecto parezca un proyecto de verdad.

Duración total: 4 horas (2 sesiones de 2 h).

📚 Qué vas a aprender

Al terminar serás capaz de:

  1. Explicar qué es un namespace y por qué evita colisiones.
  2. Declarar una clase bajo un namespace y usarla con use.
  3. Configurar Composer con autoloading PSR-4.
  4. Eliminar require_once manuales de clases.
  5. Distinguir errores, excepciones y Throwable.
  6. Crear excepciones propias que extiendan Exception/RuntimeException.
  7. Usar try/catch/finally.
  8. Configurar un manejador global de excepciones.
  9. Aplicar declare(strict_types=1) y PSR-12.
  10. Reconocer la estructura de un proyecto PHP moderno como base para Laravel.

🚀 Bloque 0 — Repaso, Composer y preparación

⏱ 25 min

✅ Antes de tocar nada: comprueba que la app funciona

No empieces a meter namespaces sin saber si el punto de partida está sano. Abre http://localhost:8080 y verifica:

  1. Login como user@demo.com / user123 → entra al catálogo.
  2. El catálogo muestra los 6 materiales.
  3. Ficha de un material (material.php?id=1) → se ve correctamente.
  4. Préstamo de un material disponible → se marca como prestado.
  5. Login como admin@demo.com / admin123 → ve el panel admin.

Si algo de esto falla, arréglalo antes de seguir. Esta actividad asume que la anterior está terminada y funcionando.

¿Qué vamos a cambiar?

🔑 Dos cambios estructurales clave:

  1. Todo el código de aplicación vive en app/ bajo App\.
  2. Solo lo que está en public/ es accesible desde el navegador. Eso es seguridad: nadie puede pedir http://localhost:8080/app/Config/db.php porque está fuera del document root.

🧠 Por qué public/ como document root

Antes, cualquier archivo en src/ era accesible desde el navegador. Si alguien ponía http://localhost:8080/config/db.php, Apache ejecutaba el PHP y podía ver credenciales si había un var_dump. Con public/ como document root:

  • Solo se sirven los archivos de public/.
  • app/, vendor/, composer.json quedan fuera del alcance del navegador.
  • Es la estructura de todos los frameworks modernos (Laravel, Symfony).

🔁 En Java con Spring, es como tener src/main/webapp/ para lo público y el resto fuera.

📄 Instalar Composer en php-fpm

Composer no viene con la imagen oficial de PHP. Lo incluiremos en php/Dockerfile:

COPY --from=composer:latest /usr/bin/composer /usr/bin/composer

Reconstruye el contenedor:

docker compose build --no-cache php-fpm && docker compose up -d

Y comprueba que se ha instalado correctamente:

docker compose exec php-fpm composer --version

Deberías ver Composer version 2.x.x.

🧪 Retos de arranque

Ejecuta composer --version dentro del contenedor. ¿Qué versión tienes? Si ves 1.x, ¿qué ha pasado?

Composer 2.x es la actual. Si ves 1.x, has instalado una versión antigua (el instalador de getcomposer.org ya da la 2.x, así que probablemente hayas usado otro método). La 2.x es la que soporta PSR-4 de forma nativa y la que usa todo el ecosistema moderno.

Abre src/repos/MaterialRepo.php y cuenta los require_once al principio. ¿Qué pasaría si mañana añades una clase Mapa y quieres usarla en el repo?

MaterialRepo.php tiene cuatro require_once: db.php, Libro.php, Revista.php, DVD.php. Si añades Mapa, tienes que acordarte de añadirlo en todos los archivos que lo usen. Si te olvidas en uno, error fatal en runtime.

Con autoloading, ese problema desaparece: escribes use App\Classes\Mapa; y Composer lo encuentra. Ese es el objetivo del Bloque 1.

Intenta abrir http://localhost:8080/config/db.php en el navegador. ¿Qué ves? ¿Es un problema de seguridad?

Ves una pantalla en blanco (o el código si Apache sirve el PHP sin ejecutarlo, según configuración). En cualquier caso, el archivo es accesible desde el navegador. Si tuviera un var_dump de las credenciales, las verías.

Sí es un problema de seguridad. Cualquier archivo de src/ es alcanzable. Por eso vamos a mover el document root a public/: solo los archivos de ahí serán servidos.

📋 Orden de los movimientos (no lo improvises)

La reorganización tiene cinco fases. Después de cada una, comprueba que la app sigue funcionando. Si algo falla, para y arréglalo antes de seguir.

📁 Fase 1 — Crear la estructura vacía

Crea las carpetas app/Classes/Traits/, app/Repos/, app/Config/, app/Includes/, app/Exceptions/, app/Services/ y public/. No muevas nada todavía.

📦 Fase 2 — Mover los archivos

Mueve cada archivo a su sitio:

  • classes/* → app/Classes/ (renombra traits/ → Traits/)
  • repos/* → app/Repos/
  • config/* → app/Config/
  • includes/* → app/Includes/
  • index.php, material.php, prestar.php, login.php, logout.php, admin.php → public/

🔧 Fase 3 — Ajustar rutas de require_once

Los archivos movidos ahora tienen rutas relativas distintas. Todavía no hay namespaces ni Composer. Arregla las rutas para que la app siga funcionando igual que antes:

  • En public/index.php: require_once __DIR__ . '/../includes/auth.php' → require_once __DIR__ . '/../app/Includes/auth.php'.
  • En app/Repos/MaterialRepo.php: require_once __DIR__ . '/../config/db.php' → require_once __DIR__ . '/../app/Config/db.php'.
  • Etc.

🌐 Fase 4 — Cambiar DocumentRoot de Apache

Edita apache/vhost.conf:

DocumentRoot /var/www/html/public

<Directory /var/www/html/public>
    AllowOverride All
    Require all granted
</Directory>

Reinicia Apache y verifica que http://localhost:8080 sigue funcionando. Si da 404, el DocumentRoot no está bien.

✅ Fase 5 — Comprobar que la app funciona

Login, catálogo, ficha, préstamo. Todo debe funcionar como antes de tocar Composer. Si algo falla, vuelve a la Fase 3.

Solo entonces pasas al Bloque 1 (crear composer.json, añadir namespaces, eliminar require_once).

⚠️ Error típico: mover index.php a public/ antes de cambiar el DocumentRoot. Resultado: 404 en todo. El orden importa.

💡 Truco: haz la Fase 2 con git mv (si usas Git) para que el historial no se rompa. Y haz un commit por fase para poder volver atrás si algo falla.

📌 Estado al terminar el Bloque 0

App verificada funcionando. Composer instalado. Entiendes por qué movemos el código a app/ y el document root a public/.

B1

📦 Bloque 1 — Namespaces, PSR-4 y autoloading

⏱ 75 min

🎯 Criterio trabajado: CE d) — carga automática mediante espacios de nombres y gestores de dependencias.

🧠 ¿Qué es un namespace?

Imagina que tú y otro compañero creáis cada uno una clase Libro. Si juntáis el código, PHP no sabe cuál es cuál: colisión de nombres. Los namespaces lo resuelven: cada clase vive en una "carpeta lógica" con nombre.

namespace App\Classes;

class Libro { ... }

La clase ahora se llama App\Classes\Libro (nombre completamente cualificado, FQN). Desde otro archivo:

use App\Classes\Libro;

$l = new Libro(...);  // PHP sabe que es App\Classes\Libro

🔁 Comparación Java: package com.app.classes; + import com.app.classes.Libro;. Idéntico concepto, sintaxis distinta.

🔑 Regla: un archivo = un namespace = una clase (convención PSR-4).

🧠 ¿Qué es PSR-4?

PSR-4 es un estándar que dice: "si tu clase se llama App\Classes\Libro, su archivo debe estar en app/Classes/Libro.php". Es decir, el namespace se mapea a carpetas.

Composer lee ese mapeo de composer.json:

{
    "autoload": {
        "psr-4": {
            "App\\": "app/"
        }
    }
}

Esto significa: "todo lo que empiece por App\ está en app/". Así, App\Classes\Libro → app/Classes/Libro.php. Composer genera vendor/autoload.php que, al incluirlo, registra un cargador automático: cuando PHP encuentra new Libro(), busca el archivo y lo incluye sin que tú hagas nada.

📌 PSR-4 es la evolución de PSR-0 (obsoleto). Usa siempre PSR-4.

🧠 Los tres comandos de Composer que vas a usar

Comando Qué hace Cuándo
composer install Lee composer.lock e instala las versiones exactas que fija el lock Primera vez, o tras clonar un repo
composer update Actualiza dependencias a sus últimas versiones compatibles y actualiza composer.lock Solo cuando quieres actualizar
composer dump-autoload Regenera solo el cargador automático (no toca dependencias) Cada vez que añades una clase nueva o cambias el mapeo PSR-4

🔑 Regla mnemotécnica: install = "pon lo que dice el lock". update = "busca versiones nuevas y actualiza el lock". dump-autoload = "recalcula dónde están mis clases".

📄 Paso 1: composer.json

Crea src/composer.json:

{
    "name": "dam/biblioteca",
    "description": "MiniApp de Biblioteca con POO, namespaces y Composer",
    "type": "project",
    "require": {
        "php": ">=8.2"
    },
    "autoload": {
        "psr-4": {
            "App\\": "app/"
        }
    },
    "config": {
        "optimize-autoloader": true,
        "sort-packages": true
    }
}

Ejecuta:

docker compose exec php-fpm sh -c "cd /var/www/html && composer dump-autoload"

Deberías ver:

Generating optimized autoload files
Generated autoload files

Y aparecerá src/vendor/ con autoload.php.

📌 composer.lock se genera automáticamente la primera vez que ejecutas composer install o composer update. Se sube al repositorio (junto a composer.json), porque fija las versiones exactas. vendor/ no se sube (se regenera con install).

📄 Paso 2: añadir namespaces a las clases

Todas las clases de app/ necesitan namespace + declare(strict_types=1) (lo veremos a fondo en el Bloque 3, pero lo ponemos ya).

app/Classes/MaterialBiblioteca.php:

<?php
declare(strict_types=1);

namespace App\Classes;

use App\Classes\Traits\TieneFechas;
use App\Classes\Traits\Loggable;

class MaterialBiblioteca implements Prestable
{
    use TieneFechas, Loggable;

    // ... resto igual ...
}

📌 Fíjate:

  • declare(strict_types=1); primera línea ejecutable, antes de namespace.
  • namespace antes de cualquier use.
  • Prestable está en el mismo namespace → no necesita use.
  • Los traits están en App\Classes\Traits → sí necesitan use.

app/Classes/Libro.php:

<?php
declare(strict_types=1);

namespace App\Classes;

class Libro extends MaterialBiblioteca
{
    // ... resto igual, SIN require_once ...
}

📌 Elimina los require_once. Composer carga MaterialBiblioteca automáticamente.

Haz lo mismo con Revista, DVD, Prestable y los traits. En MaterialRepo:

<?php
declare(strict_types=1);

namespace App\Repos;

use App\Classes\DVD;
use App\Classes\Libro;
use App\Classes\MaterialBiblioteca;
use App\Classes\Revista;
use App\Config\db;

class MaterialRepo
{
    // ... resto igual, SIN require_once ...
}

⚠️ Ojo con db(). Es una función, no una clase. Los namespaces también afectan a las funciones:

  • use App\Config\db; → importa la función (correcto).
  • O llamar \App\Config\db() (FQN, más feo).

Recomendación: use function App\Config\db; explícito. Es más legible y evita ambigüedades con clases que se llamen igual.

app/Config/db.php:

<?php
declare(strict_types=1);

namespace App\Config;

use PDO;

function db(): PDO
{
    static $pdo = null;
    if ($pdo === null) {
        // ... igual que antes ...
    }
    return $pdo;
}

📌 use PDO; es necesario porque PDO vive en el namespace global (\PDO). Dentro de namespace App\Config;, escribir PDO sin use haría que PHP buscara App\Config\PDO, que no existe.

📄 Paso 3: puntos de entrada

Los puntos de entrada son los archivos de public/ que el navegador puede pedir directamente. Son seis:

ArchivoQué hace
public/login.phpFormulario de login
public/logout.phpCierra sesión
public/index.phpCatálogo
public/material.phpFicha individual
public/prestar.phpAcción de préstamo
public/admin.phpPanel de administración

La línea imprescindible en todos ellos es esta:

require_once __DIR__ . '/../vendor/autoload.php';

Es la que registra el cargador de Composer. Sin ella, new MaterialRepo() o new Libro() darán Class not found. Va siempre la primera, antes de cualquier use.

Además, cada archivo necesita:

  1. declare(strict_types=1); justo después de .
  2. Los use de las clases que vaya a usar.
  3. El require_once de auth.php (porque auth.php no es una clase, es un archivo con funciones; Composer no lo carga automáticamente).
  4. Eliminar los require_once de clases que tuviera antes (los de MaterialRepo.php, Libro.php, etc.). Composer ya se encarga.

️ Regla clave: use solo para clases (interfaces y traits incluidos). Para funciones como requireLogin() o currentUser(), no hay use: se llaman directamente una vez incluido auth.php con require_once.

public/login.php:

<?php
declare(strict_types=1);

require_once __DIR__ . '/../vendor/autoload.php';
require_once __DIR__ . '/../app/Includes/auth.php';

// ... resto igual ...

Fíjate: vendor/autoload.php para las clases, y auth.php sigue con require_once porque tiene funciones, no clases. Los dos require son necesarios. No hay ningún use porque login.php no instancia ninguna clase.

public/logout.php:

<?php
declare(strict_types=1);

require_once __DIR__ . '/../vendor/autoload.php';
require_once __DIR__ . '/../app/Includes/auth.php';

logout();
header('Location: login.php');
exit;

Tampoco necesita use: solo llama a logout().

public/index.php:

<?php
declare(strict_types=1);

require_once __DIR__ . '/../vendor/autoload.php';
require_once __DIR__ . '/../app/Includes/auth.php';

Fíjate: ya no hay require_once de MaterialRepo. Solo vendor/autoload.php. Eso es el autoloading. auth.php, header.php y footer.php siguen con require porque no son clases.

public/material.php:

Fíjate: dos use de clases (MaterialNoEncontradoException y MaterialRepo). Ninguno de auth.

public/prestar.php:

<?php

🧪 Retos

Reto 1.1 — Abre public/index.php y elimina la línea use App\Repos\MaterialRepo;. ¿Qué error da? ¿Por qué?

Ver solución``` Fatal error: Uncaught Error: Class "MaterialRepo" not found ``` Sin `use`, PHP busca `MaterialRepo` en el namespace actual de `index.php`, que es el global. Como no existe `\MaterialRepo` (ahora es `App\Repos\MaterialRepo`), falla. Dos formas de arreglarlo: volver a poner `use App\Repos\MaterialRepo;` (recomendado), o escribir `new \App\Repos\MaterialRepo()` (FQN, más feo).

Reto 1.2 — ¿Por qué public/index.php necesita dos require_once (uno de vendor/autoload.php y otro de auth.php) pero ningún use de auth?

Ver soluciónPorque `vendor/autoload.php` solo carga clases. `auth.php` tiene funciones (`login()`, `currentUser()`, `requireLogin()`...), y Composer no las carga automáticamente por defecto. `index.php` necesita: 1. `vendor/autoload.php` → para `MaterialRepo` (clase). 2. `auth.php` → para `requireLogin()` (función). No necesita use de auth porque `auth.php` no tiene namespace y sus funciones viven en el espacio global. Un `use` ahí no tendría sentido: `use` es para importar nombres de clases, no de archivos.

Reto 1.3 — Encuentra el error. Este public/prestar.php da Class "App\Includes\auth" not found:

<?php
declare(strict_types=1);

require_once __DIR__ . '/../vendor/autoload.php';
require_once __DIR__ . '/../app/Includes/auth.php';

use App\Includes\auth;

requireLogin();
Ver soluciónEl `use App\Includes\auth;` es incorrecto: `auth` no es una clase ni un namespace declarado, es un archivo con funciones. `use` busca una clase llamada `App\Includes\auth`, que no existe, y falla al intentar resolverla. Solución: eliminar el `use App\Includes\auth;`. El `require_once` ya incluye el archivo, y las funciones quedan disponibles directamente. ```php require_once __DIR__ . '/../vendor/autoload.php'; require_once __DIR__ . '/../app/Includes/auth.php'; requireLogin(); // funciona sin use ``` Regla: `use` solo para clases, interfaces y traits. Las funciones se incluyen con `require_once` y se llaman directamente.

¿Por qué Libro.php no necesita use App\Classes\MaterialBiblioteca; pero MaterialBiblioteca.php sí necesita use App\Classes\Traits\TieneFechas;?

Libro y MaterialBiblioteca están en App\Classes. Mismo namespace = no hace falta use.

Añade una clase nueva App\Classes\Mapa (un material tipo mapa). Crea app/Classes/Mapa.php con su namespace y class Mapa extends MaterialBiblioteca. Luego úsala en MaterialRepo::hidratar() añadiendo un caso 'mapa'. ¿Qué pasos has tenido que dar?

Pasos:

  1. Crear app/Classes/Mapa.php con namespace App\Classes;.
  2. En MaterialRepo.php, añadir use App\Classes\Mapa;.
  3. En hidratar(), añadir el caso 'mapa' => new Mapa(...).
  4. Ejecutar composer dump-autoload para que Composer registre la clase.

El paso 4 es el que se olvida. Sin él, Class not found. Siempre dump-autoload después de añadir una clase.

¿Qué diferencia hay entre require_once __DIR__ . '/../vendor/autoload.php' y los require_once que tenías antes de las clases?

Antes: cada archivo incluía manualmente cada clase que usaba. Cascada de require_once que había que mantener a mano.

Ahora: una sola línea (vendor/autoload.php) registra un cargador automático. Cuando PHP encuentra new Libro(), el cargador calcula la ruta (app/Classes/Libro.php), la incluye y sigue. No hay cascada: hay carga bajo demanda.

Ejecuta composer dump-autoload y luego mira src/vendor/composer/autoload_psr4.php. ¿Qué contiene?

Un array que mapea prefijos de namespace a directorios:

return array(
    'App\\' => array($baseDir . '/app'),
);

Eso es lo que leíste de composer.json. Composer lo genera para que el cargador sepa dónde buscar. No se toca a mano: se regenera con dump-autoload.

🧠 Errores, excepciones y Throwable

En PHP moderno (7+) hay una jerarquía clara:

Throwable (interfaz)
├── Error
│   ├── TypeError
│   ├── ValueError
│   └── ...
└── Exception
    ├── RuntimeException
    ├── InvalidArgumentException
    ├── PDOException
    └── ... (y las tuyas)
  • Exception: errores "esperables" del dominio (material no encontrado, límite de préstamos). Las tuyas extienden Exception o RuntimeException.
  • Error: errores del motor de PHP (método inexistente, tipo incorrecto). No las lanzas tú.
  • Throwable: lo que captura ambas. Si quieres un catch que atrape todo, usa Throwable.

🔁 Comparación Java: Exception y Error son hermanos bajo Throwable. En PHP, desde 7, es igual.

📄 Paso 1: excepciones propias

Crea app/Exceptions/MaterialNoEncontradoException.php:

<?php
declare(strict_types=1);

namespace App\Exceptions;

use RuntimeException;

class MaterialNoEncontradoException extends RuntimeException
{
    public function __construct(int $id)
    {
        parent::__construct("No existe un material con id {$id}");
    }
}

Crea app/Exceptions/MaterialNoDisponibleException.php:

<?php
declare(strict_types=1);

namespace App\Exceptions;

use RuntimeException;

class MaterialNoDisponibleException extends RuntimeException
{
    public function __construct(string $titulo)
    {
        parent::__construct("El material '{$titulo}' no está disponible para préstamo");
    }
}

📌 Fíjate: extienden RuntimeException. Es una buena práctica: RuntimeException es para errores que ocurren durante la ejecución y que el código llamador podría querer capturar. No extiendas Exception directamente si puedes ser más específico.

📄 Paso 2: lanzar excepciones desde el repositorio (MaterialRepo.php)

Antes (findById devolvía null):

public function findById(int $id): ?MaterialBiblioteca
{
    $stmt = db()->prepare('SELECT * FROM materiales WHERE id = ?');
    $stmt->execute([$id]);
    $fila = $stmt->fetch();
    return $fila ? $this->hidratar($fila) : null;
}

Después (lanza excepción):

use App\Exceptions\MaterialNoEncontradoException;
          
public function findById(int $id): MaterialBiblioteca // Ya no necesitamos la ?
{
    $stmt = db()->prepare('SELECT * FROM materiales WHERE id = ?');
    $stmt->execute([$id]);
    $fila = $stmt->fetch();

    if ($fila === false) {
        throw new MaterialNoEncontradoException($id);
    }

    return $this->hidratar($fila);
}

⚠️ Cambio de contrato: el método ya no devuelve ?MaterialBiblioteca. Siempre devuelve objeto o lanza excepción. El ? desaparece. Todos los sitios que llamaban a findById deben actualizarse. En tu código son material.php y prestar.php. Si tienes otros, revísalos.

📄 Paso 3: PrestamoService (lógica de negocio)

💡 ¿Por qué una clase nueva? Porque prestar.php es un controlador: recibe la petición y devuelve respuesta. La lógica de negocio (comprobar disponibilidad, registrar préstamo, validar límites) no debería estar ahí. Cuando llegues a Laravel, esto se llama Servicio y es el sitio natural para esa lógica.

Crea app/Services/PrestamoService.php:

<?php
declare(strict_types=1);

namespace App\Services;

use App\Exceptions\MaterialNoDisponibleException;
use App\Repos\MaterialRepo;

class PrestamoService
{
    public function __construct(private MaterialRepo $repo) {}

    /**
     * Intenta prestar un material a un usuario.
     *
     * @throws MaterialNoDisponibleException si el material ya está prestado
     * @throws \App\Exceptions\MaterialNoEncontradoException si el id no existe
     */
    public function prestar(int $materialId, int $usuarioId): void
    {
        $material = $this->repo->findById($materialId);

        if (!$material->prestar()) {
            throw new MaterialNoDisponibleException($material->getTitulo());
        }

        $this->repo->setDisponible($materialId, false);
        $this->repo->registrarPrestamo($materialId, $usuarioId);

        $material->log(
            "Préstamo de '{$material->getTitulo()}' al usuario {$usuarioId}"
        );
    }
}

📌 Fíjate en:

  • Inyección de dependencias en el constructor: private MaterialRepo $repo (constructor property promotion, PHP 8+).
  • El método prestar() lanza excepciones, no las captura. La captura es responsabilidad del controlador.
  • Es una operación de negocio. El controlador solo llama y traduce excepciones a respuestas HTTP.

📄 Paso 4: finally — un caso real

finally se ejecuta siempre, haya o no excepción. Útil para limpiar recursos. En nuestro caso, un buen sitio es registrar siempre el intento de préstamo (éxito o fracaso): 

public function prestar(int $materialId, int $usuarioId): void
{
    $material = $this->repo->findById($materialId);

    try {
        if (!$material->prestar()) {
            throw new MaterialNoDisponibleException($material->getTitulo());
        }

        $this->repo->setDisponible($materialId, false);
        $this->repo->registrarPrestamo($materialId, $usuarioId);
    } finally {
        // Se ejecuta SIEMPRE, haya excepción o no
        $material->log(
            "Intento de préstamo de '{$material->getTitulo()}' al usuario {$usuarioId}"
        );
    }
}

📌 finally no captura: solo limpia. Si hay excepción, se propaga después del finally. Eso permite "hacer algo siempre" sin tragarte el error.

📌 htmlspecialchars($e->getMessage()): el mensaje puede contener datos del usuario (por ejemplo, un título). Escápalo siempre antes de mostrarlo.

public/prestar.php (ahora usa PrestamoService):

<?php
declare(strict_types=1);

require_once __DIR__ . '/../vendor/autoload.php';

use App\Exceptions\MaterialNoDisponibleException;
use App\Exceptions\MaterialNoEncontradoException;
use App\Includes\auth;

    header('Location: /material.php?id=' . $id);

} catch (MaterialNoEncontradoException $e) {
    http_response_code(404);
    $error = $e->getMessage();
} catch (MaterialNoDisponibleException $e) {
    http_response_code(400);
    $error = $e->getMessage();
}

📌 catch (A | B $e): PHP 7.1+ permite capturar varias excepciones a la vez si las tratas igual. Aquí las tratamos distinto (404 vs 400), así que van en catch separados.

📄 Paso 6: manejador global de excepciones

Si una excepción no se captura en ningún sitio, PHP muestra un error fatal feo. Puedes interceptarla con set_exception_handler(). Esta es la red de seguridad de tu app.

Crea app/Includes/exceptions.php:

<?php
declare(strict_types=1);

use App\Exceptions\MaterialNoEncontradoException;

set_exception_handler(function (Throwable $e): void {
    // Loguea el detalle (para el desarrollador)
    error_log('Excepción no capturada: ' . $e->getMessage());
    error_log($e->getTraceAsString());

    // Decide el código HTTP
    http_response_code(
        $e instanceof MaterialNoEncontradoException ? 404 : 500
    );

    // Muestra un mensaje genérico al usuario
    require __DIR__ . '/header.php';
    echo '<h1>Algo ha ido mal</h1>';
    echo '<p>Inténtalo de nuevo más tarde.</p>';
    require __DIR__ . '/footer.php';
    exit;
});

E inclúyelo en todos los puntos de entrada:

require_once __DIR__ . '/../vendor/autoload.php';
require_once __DIR__ . '/../app/Includes/exceptions.php';

⚠️ No muestres $e->getMessage() al usuario en el manejador global. Puede contener rutas, SQL o datos internos. Loguea el detalle, muestra un mensaje genérico. Eso es una regla de seguridad básica.

💡 Mejor aún: si vas a tener un bootstrap común, crea app/bootstrap.php y carga vendor/autoload.php + exceptions.php desde ahí. Un solo punto de arranque para toda la app.

🧪 Retos

Intenta acceder a material.php?id=9999. ¿Qué pasa ahora? ¿Y antes de las excepciones?

Ahora: findById(9999) lanza MaterialNoEncontradoException. material.php la captura, devuelve 404 y muestra un mensaje amigable.

Antes: findById devolvía null, y material.php hacía if (!$material) { http_response_code(404); exit('Material no encontrado'); }. Funcionaba, pero la lógica de "no encontrado" estaba repartida: el repositorio devolvía null, el controlador comprobaba null. Con excepciones, el repositorio decide que no encontrarlo es un error, y el controlador solo lo presenta.

¿Por qué MaterialNoDisponibleException extiende RuntimeException y no Exception directamente?

Porque RuntimeException es una categoría semántica: errores que ocurren durante la ejecución y que el código llamador podría querer capturar.

Ventaja práctica: si mañana quieres capturar todas las excepciones de runtime de tu app, puedes hacer catch (RuntimeException $e) y atrapar también las tuyas.

Encuentra el error.

Este código pretende capturar cualquier excepción, pero no captura los TypeError:

try {
    $material = $repo->findById('abc'); // string donde se espera int
} catch (Exception $e) {
    echo 'Error: ' . $e->getMessage();
}

TypeError extiende Error, no Exception. Por eso catch (Exception $e) no lo captura. Solución:

try {
    $material = $repo->findById('abc');
} catch (Throwable $e) {  // captura Exception Y Error
    echo 'Error: ' . $e->getMessage();
}

Regla: si quieres capturar todo (incluidos errores del motor), usa Throwable. Si solo quieres tus excepciones de dominio, usa Exception o una excepción propia específica.

Provoca una excepción no capturada (por ejemplo, llama a un método inexistente en index.php). ¿Qué muestra el manejador global? ¿Y qué aparece en los logs de php-fpm?

En el navegador: "Algo ha ido mal. Inténtalo de nuevo más tarde." (mensaje genérico). Código HTTP 500.

En los logs de php-fpm (docker compose logs php-fpm): el mensaje detallado y el stack trace. Eso es lo que te sirve para depurar.

La separación es intencionada: el usuario no ve detalles técnicos (seguridad), tú sí (depuración).

¿Qué diferencia hay entre catch (MaterialNoEncontradoException $e) y catch (RuntimeException $e)?

MaterialNoEncontradoException extends RuntimeException. Por tanto:

  • catch (MaterialNoEncontradoException $e) captura solo las excepciones de ese tipo exacto (o subclases suyas).
  • catch (RuntimeException $e) captura también las MaterialNoEncontradoException, y cualquier otra RuntimeException (por ejemplo, MaterialNoDisponibleException).

Cuanto más específico el catch, mejor: capturas lo que sabes manejar y dejas que lo demás suba.

¿Qué hace finally? ¿Se ejecuta si hay return dentro del try?

finally se ejecuta siempre: haya excepción, no la haya, o incluso si hay un return dentro del try o del catch. Es el sitio para limpiar recursos (cerrar ficheros, cerrar conexiones, registrar logs).

function ejemplo(): string {
    try {
        return 'desde try';
    } finally {
        echo 'esto se ejecuta siempre';
    }
}
// Imprime "esto se ejecuta siempre" y devuelve "desde try".

Cuidado: si dentro del finally hay un return, sobrescribe el del try. Mala práctica salvo casos muy concretos.

✨ Bloque 3 — Buenas prácticas y PSR-12

⏱ 40 min

🎯 Criterio trabajado: CE f) — buenas prácticas de codificación y estilos recomendados.

🧠 ¿Qué es PSR-12?

PSR-12 es el estándar de estilo de PHP FIG para código moderno. No es obligatorio, pero es lo que usan Laravel, Symfony y la mayoría de proyectos profesionales. Reglas clave:

  • Indentación con 4 espacios (no tabs).
  • Llaves de apertura de clase y método en línea nueva.
  • Una clase por archivo.
  • declare(strict_types=1) al principio.
  • Nombres: PascalCase para clases, camelCase para métodos, snake_case para variables.
  • Línea en blanco después de namespace y de cada use.
  • Visibilidad explícita en todos los métodos.

🔁 Comparación Java: equivalente a las convenciones de Oracle/Sun. Nadie te obliga, pero si no las sigues, tu código "canta".

📄 Paso 1: declare(strict_types=1)

PHP por defecto es débilmente tipado: function sumar(int $a, int $b) acepta "3" como 3. Con strict_types=1, no: lanza TypeError.

Añade declare(strict_types=1); a todos los archivos de app/ y public/, justo después de <?php. Primera línea ejecutable.

📌 Importa: sin strict types, un findById("1abc") se convierte silenciosamente en 1. Con strict, falla ruidosamente. Mejor fallar pronto que depurar después.

📄 Paso 2: tipos en todo

Revisa que todos los parámetros, retornos y propiedades tengan tipo:

// ❌ Mal
public function setTitulo($t) { $this->titulo = $t; }

// ✅ Bien
public function setTitulo(string $t): void { $this->titulo = $t; }
// ❌ Mal
public function findById(int $id) { ... }

// ✅ Bien
public function findById(int $id): MaterialBiblioteca { ... }

📌 Si un método puede devolver null, usa ?Tipo. Obliga a quien llama a comprobar el null.

📄 Paso 3: PSR-12 en la práctica

Llaves en línea nueva (clases y métodos):

// ✅ PSR-12
class Libro extends MaterialBiblioteca
{
    public function mostrarFicha(): string
    {
        // ...
    }
}

// ❌ No PSR-12
class Libro extends MaterialBiblioteca {
    public function mostrarFicha(): string {
        // ...
    }
}

Visibilidad explícita:

// ✅
public function getTitulo(): string { ... }
private function hidratar(array $fila): MaterialBiblioteca { ... }

// ❌
function getTitulo(): string { ... }  // falta public

Línea en blanco entre namespace y use:

<?php
declare(strict_types=1);

namespace App\Classes;

use App\Classes\Traits\TieneFechas;

class Libro { ... }

📄 Paso 4 (opcional, para nota): phpcs

phpcs (PHP_CodeSniffer) comprueba PSR-12 automáticamente:

docker compose exec php-fpm sh -c "cd /var/www/html && composer require --dev squizlabs/php_codesniffer"

Ejecutar:

docker compose exec php-fpm sh -c "cd /var/www/html && vendor/bin/phpcs --standard=PSR12 app/ public/"

Si hay errores, te dice línea y regla. Muchos son corregibles automáticamente:

docker compose exec php-fpm sh -c "cd /var/www/html && vendor/bin/phpcbf --standard=PSR12 app/ public/"

📌 phpcs comprueba. phpcbf corrige. Ejecuta phpcbf primero, luego phpcs para ver qué queda.

🧪 Retos

Añade declare(strict_types=1) a Libro.php. Luego llama desde cualquier sitio a new Libro('Título', 'Autor', 2020, 12345) (pasando int donde se espera string en isbn). ¿Qué error da? ¿Y sin strict_types?

Con strict_types=1: TypeError: Libro::__construct(): Argument #4 ($isbn) must be of type string, int given.

Sin strict_types: PHP convierte silenciosamente 12345 a "12345" y el objeto se crea. El error se esconde y aparece más tarde cuando menos lo esperas.

Por eso strict_types es una buena práctica: falla pronto, en el sitio donde está el bug.

Ejecuta phpcs --standard=PSR12 app/. ¿Cuántos errores salen? Elige tres y corrígelos a mano. Luego pasa phpcbf y compara.

Los errores típicos de un código que no ha seguido PSR-12:

  • Llaves de clase/método en la misma línea.
  • Falta de línea en blanco tras namespace o use.
  • Indentación con tabs.
  • Falta de visibilidad en métodos.

Corregir a mano te enseña la regla. Pasar phpcbf te la aplica automáticamente. Haz las dos cosas: primero a mano (para aprender), luego phpcbf (para el resto).

¿Por qué declare(strict_types=1) es por archivo y no global del proyecto?

Porque PHP aplica strict_types al archivo donde se declara, no a todo el proyecto. Un archivo sin declare sigue siendo débilmente tipado aunque llame a funciones de un archivo que sí lo tiene.

Consecuencia práctica: hay que ponerlo en todos los archivos. En Laravel viene por defecto en todos los archivos generados.

Mira este método y reescríbelo siguiendo PSR-12 (llaves, visibilidad, tipos):

function calcularDias($material) {
    if ($material->diasPrestamo() > 7) return $material->diasPrestamo();
    else return 7;
}
public function calcularDias(MaterialBiblioteca $material): int
{
    $dias = $material->diasPrestamo();

    if ($dias > 7) {
        return $dias;
    }

    return 7;
}

Cambios: public explícito, tipo en parámetro y retorno, llave en línea nueva, else eliminado (early return), una sola llamada a diasPrestamo(). PSR-12 no exige lo último, pero es buena práctica.
