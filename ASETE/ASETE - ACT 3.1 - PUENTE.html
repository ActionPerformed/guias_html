De la MiniApp a Laravel

En la actividad 2.2 montaste una biblioteca a mano: páginas, conexión, CRUD, escapado. En la 3.1 levantaste Laravel y viste su estructura. Este documento es el puente entre las dos cosas: tu misma aplicación, con tus mismas clases, escrita con las herramientas del framework. No es una actividad: es la explicación que va antes de la actividad en la que lo harás.

0 Antes de empezar

La idea en una frase

Lo que montaste en la 2.2 es el edificio y las tuberías. Laravel es el montaje interior. Con PHP puro, cada página que escribiste lleva dentro, a mano, las mismas cinco cosas: dónde está la ruta, cómo me conecto a la base de datos, cómo valido el formulario, cómo escapo el HTML y cómo redirijo si no estoy logueado. Escribes PHP para usar PHP, no para resolver un problema de negocio.

Laravel no te da un lenguaje nuevo: es el mismo PHP, con esas cinco piezas ya resueltas, mantenidas y conectadas entre sí. Tú escribes solo tu aplicación —las clases, las reglas, el dominio— y el framework se encarga del resto. Lo que cambia no es qué sabes, es dónde va cada cosa.

Cómo usar este documento
Para el profesor Las secciones 1, 2 y 3 son el guion del adelanto: en diez minutos puedes recorrer el árbol, la tabla de rutas y el antes/después de las clases. Las secciones 6 y 7 son el resumen que cabe en una diapositiva.
Para el alumnado Las secciones 4 a 5 (los dos caminos y cómo se escribe una página) son el corazón: léelas antes de la actividad en la que trasladas la biblioteca. La sección 7 es el guion de esa actividad, paso a paso.
Para nadie No hay cronometro, ni checklist de entregables, ni nota. Es un documento de lectura. Puedes imprimirlo o leerlo en el móvil; funciona sin conexión.

Antes de seguir: la actividad 3.1 ya tiene una tabla que conecta la 2.2 con Laravel (lo称作 «No empiezas de cero»): composer, PSR-4, el public/, las sesiones, el PDO, las excepciones. Esa tabla conecta la infraestructura. Este documento conecta la aplicación: tus páginas, tus clases, tu repositorio y tus vistas.

2 De «páginas» a «rutas»

En la 2.2, cada página es un fichero y la URL es el nombre del fichero. En Laravel hay un único punto de entrada y una tabla que dice qué URL ejecuta qué función.

ANTES La URL es el ficheroPHP

/prestar.php         →  Apache ejecuta public/prestar.php
/admin.php           →  Apache ejecuta public/admin.php
DESPUÉS La URL es una fila de una tablaPHP

Route::get('/materiales/{id}',     [MaterialController::class, 'show'])->middleware('auth');

3 · El servicio de negocio: PrestamoService

Tu versión (2.2)
app/Services/PrestamoService.phpPHP
class PrestamoService
{
    public function __construct(private MaterialRepo $repo) {}

    public function prestar(int $materialId, int $usuarioId): void
    {
        $material = $this->repo->findById($materialId);
        if (!$material->isDisponible()) {
            throw new MaterialNoDisponibleException($material->getTitulo());
        }
        $material->prestar();
        $this->repo->setDisponible($materialId, false);
        $this->repo->registrarPrestamo($materialId, $usuarioId);
    }
}
En Laravel — con transacción
app/Services/PrestamoService.phpPHP
class PrestamoService
{
    public function __construct(private MaterialRepo $repo) {}

    public function prestar(int $materialId, int $usuarioId): void
    {
        DB::transaction(function () use ($materialId, $usuarioId) {
            $material = $this->repo->findById($materialId);
            if (!$material->isDisponible()) {
                throw new MaterialNoDisponibleException($material->getTitulo());
            }
            $material->prestar();
            $this->repo->setDisponible($materialId, false);
            $this->repo->registrarPrestamo($materialId, $usuarioId);
        });
    }
}

El único cambio real: las dos operaciones (marcar no disponible + registrar el préstamo) ahora van dentro de DB::transaction(). Si la segunda falla, la primera se deshace. En PHP puro eso lo tenías que hacer a mano con beginTransaction() / rollBack()… o no hacerlo.

4 Los dos caminos

Al llegar al repositorio hay una decisión de diseño real. No es un detalle: define cuánto de tu trabajo sobrevive. Estas son las dos opciones, con sus ventajas e inconvenientes.

El repositorio desaparece. Eloquent se encarga de todo y tú escribes modelos.

app/Models/Material.phpPHP
class Material extends Model
{
    protected $fillable = ['titulo', 'autor', 'tipo'];
    protected $casts = ['disponible' => 'boolean'];
}

// y en el controlador
$material = Material::findOrFail($id);   // el 404 ya lo pone el framework
Ganas Pierdes
Menos código: CRUD, validaciones y findOrFail gratis. Tu jerarquía Libro extends MaterialBiblioteca y tu excepción MaterialNoEncontradoException.
Relaciones, with(), whereHas() y paginación nativa. El control fino del SQL: Eloquent escribe por ti y a veces por encima.

Tu aplicación no se toca; solo cambia de dónde salen los datos. Las clases siguen siendo las tuyas y Eloquent trabaja por debajo.

app/Models/Material.phpPHP
class Material extends Model
{
    protected $table = 'materiales';   // tabla única
    protected $fillable = ['titulo', 'autor', 'tipo'];
}
app/Repos/MaterialRepo.phpPHP
public function findById(int $id): MaterialBiblioteca

        throw new MaterialNoEncontradoException($id);
    }

Ganas Pierdes
Todo tu código 2.2 sobrevive: dominio, excepciones, traits, servicio. Escribes «a mano» el mapeo entre filas y objetos (tu hidratar()).
El repositorio sigue siendo tu: decides tú qué se consulta y cómo. Relaciones y paginación las montas tú sobre Eloquent.

La dificultad de Eloquent con jerarquías: una tabla materiales con columna tipo es «herencia de tabla única». Eloquent, por defecto, te devuelve un Material genérico: hay que enseñarle a hidratar un Libro cuando tipo='libro' (con un newFromBuilder() en el modelo base o con una factoría). Es el precio de usar el ORM con una jerarquía: tu jerarquía la controlas tú.

Mi recomendación para esta actividad: el camino B. Y no por comodidad, sino por lo que enseña:

  • Porque el objetivo de la actividad es el salto conceptual, no el ahorro de líneas. Con el camino B el alumno ve que Laravel no le obliga a rediseñar su aplicación: le deja cambiar la infraestructura. Ese es, de verdad, el mensaje del módulo.
  • Porque lo que hay que evaluar en un examen es su dominio (que la excepción se lance en el sitio correcto, que el servicio lance MaterialNoDisponibleException cuando toca). Si el camino A borra las clases, dejas de poder evaluar eso.
  • Porque con el camino B el cambio es de una línea (Material::find($id) en lugar del prepare/execute), y se ve con claridad que la app sigue siendo la suya.

Y un apunte honesto: en un proyecto real de producción, el camino A (Eloquent puro) suele ganar, porque las relaciones y la paginación hacen buena parte del trabajo. No presentes el camino B como «el único correcto», sino como el camino que te deja medir lo que has aprendido.

5 Cómo se escribe una página

Tres piezas: la ruta (qué URL hace qué), el controlador (qué hace) y la vista (cómo se ve). Vamos a escribir la ficha de un material, que es tu public/material.php.

routes/web.phpPHP
use App\Http\Controllers\MaterialController;

Route::get('/materiales/{id}', [MaterialController::class, 'show'])
    ->middleware('auth');
  • {id} es un parámetro de ruta: la URL /materiales/3 lo entrega al controlador. Ya no hay ?id=3 ni $_GET.
  • ->middleware('auth') es tu requireLogin(), pero escrito una vez y protegido por el framework.
  • Para verlo: php artisan route:list. Te dice qué URL existe, qué método y qué middleware.
app/Http/Controllers/MaterialController.phpPHP
class MaterialController extends Controller
{
    public function __construct(private MaterialRepo $repo) {}

    public function show(int $id)
    {
        try {
            $material = $this->repo->findById($id);   // lanza TU excepción
        } catch (MaterialNoEncontradoException $e) {
            abort(404, $e->getMessage());        // tu 404 de siempre
        }

        return view('materiales.show', ['material' => $material]);
    }
}
  • El try/catch con tu excepción propia sigue igual. Lo que cambia es que ahora el catch produce una respuesta (abort(404)) en lugar de http_response_code(404); exit(...).
  • private MaterialRepo $repo en el constructor: ya lo escribiste en PrestamoService (inyección por constructor, PHP 8+). En Laravel, además, el framework instancia el repositorio por ti y te lo inyecta: es el contenedor de dependencias. Desaparecen los new MaterialRepo().
  • El controlador no hace echo: devuelve. El framework convierte ese retorno en una respuesta HTTP.
resources/views/materiales/show.blade.phpblade
@extends('layouts.app')

@section('titulo', $material->getTitulo())

@section('contenido')
    <h1>{{ $material->getTitulo() }}</h1>
    <p>{{ $material->getAutor() }}</p>

    @if (!$material->estaDisponible())
        <form method="POST" action="{{ route('prestamos.store') }}">
            @csrf
            <button type="submit">Prestar</button>
        </form>
    @endif
@endsection
  • {{ }} escapa el HTML por ti: es tu htmlspecialchars() resuelto. Y el {{ }} de Blade, no el de JavaScript: la interpolación es de PHP.
  • {{ route('prestamos.store') }} genera la URL: nunca más escribes la URL a mano. Si cambias la ruta en routes/web.php, la vista se actualiza sola.
  • @csrf es el token de seguridad: en Laravel es obligatorio en los formularios POST.
resources/views/layouts/app.blade.phpblade
<!DOCTYPE html>
<html lang="es">
<head>
    <title>@yield('titulo')</title>
</head>
<body>
    @include('partials.navbar')
    @yield('contenido')
</body>
</html>
  • @extends + @yield sustituyen a tu require header.php y require footer.php: el esqueleto se declara una vez y cada página rellena sus huecos.
  • Es el mismo concepto que tu header.php, pero con dos ventajas: las páginas se nombran (materiales.show) y no son ficheros sueltos en un directorio.

6 Lo que cambia por dentro

El resumen que cabe en una diapositiva. Cada fila es un trozo de PHP que ya conoces y su equivalente.

En la 2.2 En Laravel Qué has ganado
$_POST['titulo'] $request->input('titulo') Con un Form Request, la validación ocurre antes de que el controlador se ejecute.
trim($_POST['titulo']) === '' 'titulo' => 'required|max:150' Una línea en lugar de un if; y devuelve 422 con los errores ya formateados.

session_start() / $_SESSION['rol'] auth()->user() + middleware El requireLogin() se pone en la ruta, una vez, y protege a todas.

mariadb/init.sql migraciones (php artisan migrate) El esquema pasa a ser código versionado: si mañana añades una columna, lamigration la añade.

8 Lo que no cambia

Para cerrar: la lista de lo que no cambia. Si alguien pregunta «¿y ahora tengo que saberme Laravel?», la respuesta es esta.

  • PHP. El mismo lenguaje. Tus clases, tus traits, tus interfaces, tus excepciones, tu declare(strict_types=1).
  • Los namespaces y PSR-4. Ya los dominas: en Laravel son idénticos.
  • Composer. El mismo fichero, la misma clave psr-4.
  • MariaDB y el SQL. Solo cambia quién escribe el SELECT.
  • La lógica de negocio. PrestamoService sigue siendo tuyo y sigue siendo lo más valioso de tu aplicación.
  • El try/catch con excepciones propias. Sigue siendo la forma correcta de manejar «material no encontrado» o «no disponible».
  • La inyección por constructor. Ya la usas en PrestamoService. Laravel simplemente la completa.

La frase para el aula: «En la 2.2 habéis construido la biblioteca a mano: las páginas, la conexión, el CRUD, el escapado. En Laravel seguís teniendo la misma biblioteca —vuestras mismas clases, con vuestro mismo Composer y vuestros mismos namespaces—; lo que cambia es que el framework se encarga de la fontanería: las rutas, la base de datos, las plantillas y los errores. Vosotros ya habéis hecho la parte difícil.»

Y un matiz honesto: Laravel tiene curva de aprendizaje propia. No es «PHP con más cosas»: es una forma de organizar (convención sobre configuración). La 2.1 y la 2.2 (POO, repositorio, namespaces, Composer) existen precisamente para que el salto sea manejable: vas a escribir código dentro de sus convenciones, no a aprender un lenguaje nuevo.

9 Retos de comprensión

Seis preguntas para comprobar que el puente está entendido. Sirven como repaso en el aula o como autoevaluación antes de la actividad.

1En tu proyecto de la 2.2, la URL /material.php?id=3 carga la ficha de un material. En Laravel, ¿qué URL carga esa misma ficha y por qué cambia?
En Laravel la URL es /materiales/3. La razón es que la URL deja de ser el nombre del fichero: pasa a ser una fila de la tabla de routes/web.php, y el 3 es un parámetro de ruta ({id}) que llega al controlador ya tipado como int. Con la ruta antigua habría que recibirlo en $_GET y validarlo a mano.
2Tu public/material.php empieza con requireLogin(). En Laravel, ¿dónde va esa comprobación y qué se gana?
Va en la ruta: ->middleware('auth'). Se gana que se escribe una vez y protege a todas las rutas que quieras; además el framework responde con su propia página de login en lugar de tu exit(). Y el rol se resuelve igual con un middleware rol:admin.
3En la 2.2 escribiste db()->prepare('SELECT …') dentro de MaterialRepo. En el camino B, ¿qué línea sustituye a ese prepare y qué queda intacto?
La sustituye $fila = Material::find($id); (Eloquent). Qeda intacto todo lo demás: tu excepción MaterialNoEncontradoException, tu hidratar() y el contrato del método. Lo único que cambia es de dónde sale la fila.
4Tu PrestamoService ya usa inyección de dependencias por constructor (private MaterialRepo $repo). ¿Qué cambia al llevarlo a Laravel?
El constructor no cambia. Lo que cambia es que el framework instancia el repositorio por ti y te lo inyecta en el controlador: no escribes new MaterialRepo() en ninguna parte. Eso es el contenedor de dependencias de Laravel. La inyección por constructor ya la entendías tú.
5En tu header.php y footer.php usabas require y htmlspecialchars(). ¿Qué los sustituye en Blade?
@extends + @yield sustituyen a los require: el esqueleto se declara una vez en layouts/app.blade.php y cada vista rellena sus huecos. Y {{ }} sustituye a htmlspecialchars(): Blade escapa por defecto. Además {{ route('prestamos.store') }} genera las URLs.
6Tu mariadb/init.sql creaba las tablas. ¿Qué lo sustituye en Laravel y qué ventaja tiene?
Las migraciones: ficheros PHP versionados, uno por cambio de esquema, que se aplican con php artisan migrate. La ventaja es que el esquema pasa a ser código: cuando añadas una columna escribirás una migración nueva y migrate la aplica, en vez de editar el SQL a mano y acordarte de ejecutarlo en los seis ordenadores del aula.
