1¿Qué es Git?

Git es un sistema de control de versiones distribuido creado por Linus Torvalds en 2005. Guarda el historial de cambios de tu proyecto para que puedas: volver atrás si algo se rompe, trabajar en paralelo con compañeros, experimentar en ramas y saber quién cambió qué, cuándo y por qué.

Vocabulario mínimo

Repositorio
Carpeta gestionada por Git; el historial vive en .git.
Commit
«Foto» del proyecto en un momento, con un hash.
Rama (branch)
Línea de trabajo independiente. La principal: main.
HEAD
Puntero a dónde estás ahora.
Remoto
Copia en un servidor (GitHub, GitLab…).
Merge
Fusionar una rama en otra. Si Git no puede, hay conflicto.
⚠️ Aviso: la carpeta .git contiene TODO el historial. No la borres ni la edites a mano. Jamás.

3¿Dónde guardo mi repo local? ⭐

Regla de oro: un repositorio = una carpeta de proyecto. Todo lo de dentro se versiona; lo de fuera no. Nunca metas un repo dentro de otro.
⚠️ Aviso: no guardes repos en OneDrive, Google Drive ni Dropbox. Sincronizan en tiempo real y pueden corromper .git.

Estructura típica

mi-proyecto/        ← raíz del repositorio
├── .git/           ← oculta, historial (NO TOCAR)
├── .gitignore      ← qué ignorar
├── README.md       ← descripción
└── src/            ← tu código

¿Varios equipos? El repo es portable (copia la carpeta con .git) o, mejor, usa git clone en cada equipo. No subas .git a un ZIP compartido si hay datos sensibles.

4Flujo de trabajo básico

1. git status          # ¿qué ha cambiado?
2. git add <archivo>   # preparo cambios
3. git commit -m "..." # confirmo
4. git push            # subo al remoto
git init                          # desde cero
git clone https://github.com/usuario/repo.git   # crea la carpeta solo
git add archivo.txt | carpeta/ | .
git commit -m "Añade función de login"
git log --oneline --graph
Buenos mensajes: imperativo («Añade login»), primera línea ≤ 50 caracteres, explica el qué y el por qué. Ej.: fix: corregir validación de email

Deshacer

git restore archivo.txt            # descarta cambios del working dir
git restore --staged archivo.txt   # saca del staging, sin perder cambios
git reset --soft HEAD~1            # deshace el último commit, mantiene cambios
git reset --hard HEAD~1            # ⚠️ BORRA el commit y sus cambios

🧪Laboratorio: terminal + grafo

Terminal simulada (sin riesgo). Escribe comandos o usa los botones. Soporta git init, status, add, commit -m, branch, switch [-c], checkout, merge, log --oneline, remote add, push, pull, clone, además de touch <archivo> para crear/modificar archivos.

    5Ramas (branches)

    git branch                  # listar
git switch -c nueva-rama    # crear Y cambiarse
git switch main             # volver (checkout es el equivalente antiguo)
git merge nueva-rama        # fusionar en la actual
git branch -d nueva-rama    # borrar si ya está fusionada

    Si hay conflicto, edita los archivos, busca <<<<<<<, =======, >>>>>>>, decide qué queda y luego git add archivo + git commit.

    Guardar a medias: stash

    git stash          # guarda cambios temporalmente
git stash list     # ver guardados
git stash pop      # recupera el último y lo borra
git stash apply    # recupera sin borrarlo
git stash drop     # borra el último

    6Repositorios remotos

    git remote add origin https://github.com/usuario/repo.git
git remote -v
git push -u origin main   # primera vez
git push                  # después
git pull                  # fetch + merge
git fetch                 # solo trae

    7Autenticación: HTTPS vs SSH ⭐

    HTTPS (fácil al inicio)

    Pide usuario y token personal (PAT), no la contraseña: Settings → Developer settings → Tokens. Usa Git Credential Manager; credential.helper store lo guarda en texto plano ⚠️.

    ✔ rápido · ✘ tokens que caducan
    SSH (recomendado a medio plazo)

    No pide credenciales nunca más y es más seguro.

    ✔ seguro · ✘ setup inicial más lento
    ssh-keygen -t ed25519 -C "tu@email.com"
cat ~/.ssh/id_ed25519.pub      # pégala en GitHub → Settings → SSH and GPG keys
ssh -T git@github.com          # probar
git clone git@github.com:usuario/repo.git
git remote set-url origin git@github.com:usuario/repo.git   # pasar un repo de HTTPS a SSH

    8Colaborar: forks y Pull Requests ⭐

    Con permisos de escritura

    1. git clone <url>
2. git switch -c feature/mi-tarea
3. ... editar, add, commit ...
4. git push -u origin feature/mi-tarea
5. Abrir Pull Request hacia main → compañero revisa → Merge
6. git switch main && git pull

    Con fork (sin permisos)

    ① Fork en GitHub → ② clona tu fork → ③ rama, commits y push a tu fork → ④ Compare & pull request al original → ⑤ el mantenedor acepta o pide cambios.

    git remote add upstream https://github.com/original/repo.git
git fetch upstream && git switch main
git merge upstream/main && git push origin main

    11Alias y atajos ⭐

    git config --global alias.st "status"
git config --global alias.co "checkout"
git config --global alias.br "branch"
git config --global alias.ci "commit"
git config --global alias.lg "log --oneline --graph --all --decorate"
git config --global alias.undo "reset --soft HEAD~1"

    Uso: git st · git lg (historial bonito) · git undo (deshace el último commit manteniendo cambios).

    12Buenas prácticas

    1. Commits pequeños y frecuentes: un commit = un cambio lógico.
    2. Mensajes claros, piensa en tu «yo» del futuro.
    3. Nunca subas secretos (contraseñas, tokens, .env).
    4. Ramas para nuevas funcionalidades: feature/login.
    5. pull antes de push para evitar conflictos.
    6. .gitignore desde el principio (¡sobre todo con node_modules!).
    7. Aprende a leer los conflictos; no borres archivos a lo loco.
    8. Publica tus prácticas en GitHub: es tu portfolio.
    9. No toques .git a mano.
    10. Carpeta dedicada (~/dev, C:\dev): nunca Escritorio, Descargas ni OneDrive.
    11. Un repo = un proyecto.
    12. git reflog antes de entrar en pánico: casi todo se recupera.
